# Score govocal-ds against six live Storybooks

The next govocal-ds audit should first score six public Storybooks with the same rubric it applies to itself. Companies and governments ship all six, and all were rebuilt between late September and October 2026. **Amsterdam's city design system** is the closest civic peer: it runs the same Storybook minor version, has an AI connection and has handbook-grade pages. **Culture Amp's Kaizen** is built on React Aria and has the best right-to-left (RTL) practice. **SumUp's Circuit UI** has one team owning components, tokens and lint rules, all documented in one Storybook with written lifecycle promises. **Workday's Canvas Kit** brings back-office accessibility guides and documentation for AI agents. **Bitwarden** has real admin screens and 102 scripted tests inside its Storybook. **Norway's Designsystemet** is one system shared by a community of 300+ organisations, with an accessibility check on every story. A dozen other Storybooks each lend one lesson. NL Design System shows how to theme many cities through tokens. React Spectrum S2 and Hopper show a styling API that accepts only tokens. Grafana and monday.com's Vibe show pages that teach designers. No public system runs govocal-ds's exact model, in which designers own agent-built component code that developers import, so the benchmark borrows parts. govocal-ds already leads on one of them: no civic Storybook checked shows every story in Arabic right-to-left. Some design work keeps its value whatever developers decide: tokens in a standard format with a grammar and declared contrast pairs; one vocabulary from token name to button label; behaviour specs and tests that a rebuild on another base library must pass; a page anatomy a designer can run; and an API that keeps styling inside the system. Developers keep four calls: the base library, how the code reaches their apps, the integration seams, and the terms of adoption. The proposed rubric gives 85 points to design-owned work and 15 to how well the Storybook prepares developers' decisions. Each criterion is scored 1 to 5 on evidence. The total is capped at 60 if any design dimension is close to empty or if a single invented or off-token value turns up in component code. Back-office accessibility is scored on complete, honest reporting, never on a blocking gate.

## Six live Storybooks form the scoring panel

The panel came from more than forty candidates checked live on 29 October 2026. Every public Storybook serves two files that make such a check possible. `index.json` lists every sidebar entry with its tags. `project.json` gives the Storybook version, build date and add-ons ([Storybook indexers](https://storybook.js.org/docs/api/main-config/main-config-indexers)). The audit can recount govocal-ds from the same two files, so the comparison is like for like. To join the panel, a Storybook had to be live, rebuilt in 2026, owned by an organisation for its own product, and carry real guidance. That last test matters for a design bible. In one group of systems the Storybook *is* the documentation: Canvas Kit, Vibe, Circuit, Grafana and Amsterdam. In the other it is a developer workbench and the guidance lives on a separate site. Elastic's Storybook, for example, holds **zero docs pages** ([EUI index.json](https://eui.elastic.co/storybook/index.json)). The bible belongs in the first group. No single system matches govocal-ds's mix of a civic product, many city brands, right-to-left languages, a table-heavy back office and code built by designers with AI agents, so the panel splits the job six ways.

If the audit could study only one system, it should be Amsterdam. It is a city. It runs Storybook 10.6 with the same MCP add-on govocal-ds uses. ## Seven pieces of design work hold whatever developers decide

Under the model the project lead has set, the design side owns more than most design teams do. It owns the tokens, docs and stories, and also the component code and its API. Designers acting as junior front-end developers and design-system architects build it with AI coding agents, optionally starting from Figma, and own any Figma sync. Developers never open Figma; they import the components and compose screens. The components are not a throwaway reference: they and their API are design's product. That puts code quality on design's side of the ledger. "Design-owned" here means everything inside the Storybook that would still be valuable if developers swapped React Aria for another base library, changed how the code reaches their apps, or took a year to decide. Seven pieces of work pass that test. Each answers one of the developers' doubts (strong, cemented in tokens, consistent variables and language) or serves the designer who will run the Storybook as her design bible.

### Tokens a skeptic can break and watch fail

Tokens are the named values, such as colours, spacing and type sizes, that components read instead of raw numbers. "Standard tokens" now has a fixed meaning. The Design Tokens Community Group's JSON format reached its first stable edition, 2025.10, on 28 October 2025, with theming and multi-brand support ([W3C DTCG](https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/)). It is a vendor-backed community specification, not a W3C Recommendation. Figma added native import and export in that format in November 2025, but only for single values: dimensions must be in px, durations in seconds, and composites such as typography are not supported ([Figma Help](https://help.figma.com/hc/en-us/articles/15343816063383-Modes-for-variables); [Figma Schema 2025](https://www.figma.com/blog/schema-2025-design-systems-recap/)). That gives each of govocal-ds's hand-written "Not in Figma" motion and size tokens a concrete test: move it into Figma, or name the Figma limit that keeps it out. The handover that survives any stack is the token JSON, not the generated `tokens.css`, because one JSON source can build CSS variables, a JavaScript theme or a Sass map ([Style Dictionary formats](https://styledictionary.com/reference/hooks/formats/predefined/)).

Naming quality can be tested by machine. Primer and NL Design System publish token grammars with four things in common: a fixed order of name parts, a required last part naming the CSS property, role words rather than colour words in the semantic layer, and state as its own part ([Primer token names](https://primer.style/product/primitives/token-names/); [NL Design System token convention](https://nldesignsystem.nl/handboek/developer/design-token-conventie/)). Adobe even ships a tool that audits token names for overloaded values ([Spectrum design data tools](https://opensource.adobe.com/spectrum-design-data/tools/)). The direction rule matters more than the number of layers. Raw "primitive" tokens feed semantic tokens, and components read only semantic tokens, never primitives.

The risk that comes with AI agents is invented tokens. A 2026 write-up of an eight-agent pipeline building a React menu found **27 fabricated tokens while every test passed**, because behaviour tests do not check appearance ([kaelig.fr](https://www.kaelig.fr/design-system-components-with-ai-agent-teams/)). Atlassian lists "wrong token names" and "icons that seem on-brand but don't exist" among the failures it saw at scale ([Atlassian](https://www.atlassian.com/blog/how-we-build/turning-handoffs-into-handshakes-integrating-design-systems-for-ai-prototyping-at-scale)). A CSS variable that does not exist fails silently, so the proof has to be an existence check. Stylelint's core `no-unknown-custom-properties` rule flags any `var(--gv-…)` that is not defined in the token file ([Stylelint](https://stylelint.io/user-guide/rules/no-unknown-custom-properties/)). A stock rule that developers recognise, configured strictly, is stronger evidence than a custom test written by the same agents that wrote the CSS. The project's decision that token values win over off-token design values fits here. Every stray value found in a design or in component CSS is snapped to the nearest token, and the audit never rewards adding a token to match a stray value.

Contrast and city theming complete the token work. Contrast can be proven when each text-on-background pairing is declared as data and linted, the way Terrazzo's `a11y/min-contrast` rule checks the token source ([Terrazzo lint](https://terrazzo.app/docs/linting/)). Each `color-mix()` stand-in then needs its computed value checked in every mode, because no token linter can see a value that only exists at runtime. For many cities, NL Design System is the model. Its components carry no house style, every organisation's theme uses the same component token names, and **48 organisation themes, mostly municipalities, render in one Storybook** ([NL Design System tokens](https://nldesignsystem.nl/handboek/huisstijl/design-tokens/); [themes index.json](https://nl-design-system.github.io/themes/index.json)). The design-owned deliverable is a written tenant boundary, saying which tokens a city may set and which it never may, plus a swap test. In the swap test, a fictional second city changes only the allowed values, and every story re-themes with no component edits. There is room to lead here. **86% of teams have tokens but only 66% document them** ([zeroheight 2026](https://report.zeroheight.com/2026)). No exemplar publishes a token-coverage percentage; the only public figure is a vendor study's **40.4% average across 375 sites** ([OverlayQA](https://overlayqa.com/blog/design-token-drift-study/)).

### One vocabulary from token name to button label

The developers' second doubt, "consistent variables and language", plays out on three layers. The first is component names. They should follow the consensus across design systems, which component.gallery and Open UI record along with aliases: Modal is also called Dialog, Toast is also called Snackbar ([Component Gallery](https://component.gallery/components/); [Open UI matrix](https://open-ui.org/research/component-matrix/)). Wherever govocal-ds uses a different name, its naming file should log the alias. The second is the concept vocabulary, the layer most at risk when agents write code. It needs one size scale everywhere, values that name intent rather than appearance (`primary`, never `blue`), and one word per concept, for example *variant* for emphasis, *tone* for semantic colour and *size* for scale ([designsystems.one naming](https://www.designsystems.one/foundations/naming-conventions)). The API is design's, so these names are design's. A script can count synonyms across the components manifest (Storybook's machine-readable list of every component and prop); the target is one name per concept. Primer's September 2026 audit shows what drift looks like: one `size` scale said "normal" where another said "medium" ([Primer #8384](https://github.com/primer/react/issues/8384)).

The third layer is copy, and it is the weakest in the industry: only **38% of systems include UX copy guidelines, and 21% are satisfied with them** ([zeroheight 2026](https://report.zeroheight.com/2026)). The best examples are Vibe's UX Writing Handbook, Grafana's Voice and Tone page, Circuit's Content guidelines on every component and Amsterdam's "How to write" sections ([Vibe handbook](https://vibe.monday.com/?path=/docs/foundations-ux-writing-handbook--docs); [Grafana Voice and Tone](https://developers.grafana.com/ui/latest/?path=/docs/docs-overview-voice-and-tone--docs); [Circuit Button.mdx](https://github.com/sumup-oss/circuit-ui/blob/HEAD/packages/circuit-ui/components/Button/Button.mdx); [Amsterdam Button docs](https://github.com/Amsterdam/design-system/blob/main/storybook/src/components/Button/Button.docs.mdx)). GOV.UK goes furthest, with an exact label for each situation: "Continue" when data isn't saved, "Save and continue" when it is ([GOV.UK Button](https://design-system.service.gov.uk/components/button/)). Go Vocal sells to cities in many languages, so one rule matters a great deal: every visible string reaches the component as a prop and is never stitched together from pieces. That is a design rule that holds whatever translation library developers pick ([Carbon checklist](https://www.carbondesignsystem.com/getting-started/contributing/component-checklist)). A prose linter such as Vale, fed a govocal-ds word list that includes the civic terms (participant, input, project, phase), turns "consistent language" into a check anyone can rerun ([Vale](https://vale.sh/)).

### An API and styling boundary that keep the language in design's hands

When developers compose screens and design controls the visual language, the component API is where that control lives. The strictest public model is React Spectrum S2, which is built on React Aria. Its `styles` prop "accepts a limited set of CSS properties, including layout, spacing, sizing, and positioning. Other styles such as colors and internal padding cannot be customized." Its escape hatches (props that let a consumer override styling) are honestly named `UNSAFE_className` and `UNSAFE_style` ([React Spectrum styling](https://react-spectrum.adobe.com/styling)). Workleap's Hopper, also on React Aria, accepts only tokens in style props by default and allows `UNSAFE_` values on a short whitelist ([Hopper styling](https://github.com/workleap/wl-hopper/blob/main/apps/docs/content/styled-system/concepts/styling.mdx)). The trend in 2025–2026 points the same way. Primer v38 removed its `sx` styling prop ([Primer v38](https://github.com/primer/react/discussions/7086)), and Canvas Kit deprecated style props to "promote prescriptive, opinionated styling" ([Canvas Kit migration](https://workday.github.io/canvas-kit/?path=/docs/guides-style-props-migration-overview--docs)). Layout primitives complete the boundary. Grafana types its Stack's `gap` to spacing tokens, and Amsterdam limits its Grid's `gap` to a short list of names, so screens need no custom CSS ([Grafana Stack.tsx](https://github.com/grafana/grafana/blob/HEAD/packages/grafana-ui/src/components/Layout/Stack/Stack.tsx); [Amsterdam Grid.tsx](https://github.com/Amsterdam/design-system/blob/main/packages/react/src/Grid/Grid.tsx)). Vibe's Flex also accepts a raw number, which is a weaker guard ([Vibe Flex.types.ts](https://github.com/mondaycom/vibe/blob/HEAD/packages/components/layout/src/Flex/Flex.types.ts)). The counter-example sits in the React Aria peer group. B.C. Gov's Button sets its own classes and then spreads the consumer's props after them, which on a reading of the source lets a consumer's class replace the system's styling ([B.C. Button.tsx](https://github.com/bcgov/design-system/blob/main/packages/react-components/src/components/Button/Button.tsx)).

An API that other people build on also needs written rules and a visible surface. Primer keeps its API conventions as numbered decision records and had an agent audit its components against them ([Primer #8384](https://github.com/primer/react/issues/8384)). React Spectrum generates its public API as a text file that is compared on every change ([S2 api-diff.md](https://github.com/adobe/react-spectrum/blob/main/packages/@react-spectrum/s2/api-diff.md)). For govocal-ds, that means design writes the conventions down and publishes an API diff so developers can see every change. It also means component CSS that drops into any app cleanly: named cascade layers, one stylesheet, no global element selectors and no runtime style injection. Primer measured runtime injection at **242 ms for 1,000 components, against 96 ms for static CSS** ([Primer ADR-016](https://github.com/primer/react/blob/main/contributor-docs/adrs/adr-016-css.md); [ADR-021](https://github.com/primer/react/blob/main/contributor-docs/adrs/adr-021-css-layers.md)). A closed boundary also serves the long-term goal. An agent composing screens on behalf of a product manager cannot drift the visual language if the API gives it no way to.

### Behaviour specs and tests that survive a new base library

React Aria supplies keyboard, focus and screen-reader behaviour today, and developers may replace it. The design side protects its own work by writing behaviour as outcomes rather than library calls. Each interactive component names its pattern in the W3C ARIA Authoring Practices Guide (APG), which describes how each kind of widget responds to Tab, the arrow keys, Enter and Escape ([W3C APG](https://www.w3.org/WAI/ARIA/apg/patterns/)), and carries a keyboard table in plain words. The tests follow the same rule. Storybook's interaction tests are scripted clicks and keystrokes inside a story. They should find elements by role and label, the way a person does, with test IDs as "a last resort" ([Storybook interaction tests](https://storybook.js.org/docs/writing-tests/interaction-testing)). Tests written this way check what a person experiences, so a rebuild on another base library can be accepted by passing the same stories. Visual baselines work the same way: screenshots approved once, then compared on every change. The split below shows what "React Aria may be dropped, and that is fine" means in practice. It is assembled from Kaizen, which keeps its Usage page free of React Aria and lists "additional React Aria and native HTML props" separately on the API page ([Kaizen API spec](https://github.com/cultureamp/kaizen-design-system/blob/main/packages/components/src/Button/_docs/Button--api-specification.mdx)), and from B.C. Gov, which names its base library on every page ([B.C. Button.mdx](https://github.com/bcgov/design-system/blob/main/packages/react-components/src/stories/Button.mdx)).

| Survives a base-library swap unchanged | Design rebuilds on the new base |
|---|---|
| Tokens, component CSS, stories and visual baselines | The behaviour wiring inside each component |
| Usage pages, specs written against APG patterns, copy rules, RTL rules | Props passed straight through from the base library, such as press events and render props |
| Interaction tests that find elements by role and label, reused as acceptance tests for the rebuild | Locale-aware date and number formatting, which React Aria's provider supplies today |
| The component API, as long as it uses design's own vocabulary | Any API names copied from the base library without a reason |

States and edge cases are where two implementations of the same component drift apart, so they belong in stories. Carbon defines four empty states: no data yet, no results, data blocked by an error or permission, and starter content ([Carbon empty states](https://carbondesignsystem.com/patterns/empty-states-pattern/)). AgDS shows loading, empty, error and final states for its data views ([AgDS data loading](https://design-system.agriculture.gov.au/storybook/?path=/story/patterns-data-loading-table--basic)). Primer adds a matrix story with every combination of variant and state ([Primer All Combinations](https://primer.style/react/storybook/?path=/story/components-actionlist-examples--all-combinations)). Translation sets the budget for text: English labels of ten characters or fewer can grow 200–300% in other languages ([W3C i18n](https://www.w3.org/International/articles/article-text-size), older but still the reference). Density follows audience, as Amsterdam's spacious and compact modes show ([Amsterdam modes](https://amsterdam.github.io/design-system/?path=/docs/docs-guidelines-modes--docs)). Right-to-left is govocal-ds's clearest lead. No public-sector Storybook checked shows every story in an RTL script. The nearest are Kaizen's 79 RTL sticker sheets, with a toolbar that flips direction and sets React Aria's locale to Arabic, and S2's 35-locale picker ([Kaizen preview.tsx](https://github.com/cultureamp/kaizen-design-system/blob/main/docs/.storybook/preview.tsx); [S2 constants.js](https://github.com/adobe/react-spectrum/blob/main/.storybook-s2/constants.js)). The audit should confirm the claim is real. That means logical CSS properties (start and end rather than left and right), a published list of which icons mirror and which don't, and Arabic strings rather than English text flipped.

Accessibility follows the project's decision: WCAG 2.2 AA is the front office's bar, and back-office findings are reported, never blocking. The benchmark treats reporting as serious work, not a lower standard. Automated checks catch only part of the picture. Storybook says axe, the standard automated checker, "catches up to 57% of WCAG issues" ([Storybook a11y](https://storybook.js.org/docs/writing-tests/accessibility-testing)), and GitHub puts the share of A/AA criteria that automation can detect at **64%** ([GitHub blog](https://github.blog/ai-and-ml/github-copilot/building-a-general-purpose-accessibility-agent-and-what-we-learned-in-the-process/)). What makes a report credible is coverage and honesty: axe run on every story; results published per component, the way IBM Carbon publishes an accessibility status page ([Carbon status](https://www.carbondesignsystem.com/building-blocks/core/components/overview/accessibility-status)); manual screen-reader and keyboard notes for the complex widgets; and a per-component checklist of what the person composing a screen still owns. NL Design System tags each item of that checklist by role and WCAG criterion ([NL DS acceptance criteria](https://raw.githubusercontent.com/nl-design-system/candidate/main/packages/docs/form-field-error-message-docs/docs/acceptance-criteria.md)). GitHub found that **nearly 48% of its accessibility audit issues were preventable** by writing down intent upfront, which is design-side work ([GitHub annotation toolkit](https://github.blog/enterprise-software/collaboration/level-up-design-to-code-collaboration-with-githubs-open-source-annotation-toolkit/)). Designsystemet, B.C. Gov and Singapore's SGDS make violations fail the build ([Designsystemet preview.tsx](https://github.com/digdir/designsystemet/blob/main/apps/storybook/.storybook/preview.tsx)). Storybook documents a gradual path there, marking known violations "todo" first ([Storybook a11y](https://storybook.js.org/docs/writing-tests/accessibility-testing)). The Storybook should describe that as a later option for the front office, not as a gate for the back office.

### A bible a designer with taste can run

No exemplar has the whole component page, but together they define it. From Circuit: a status badge, then "When to use it", usage and Content guidelines. From Grafana: Do's and Don'ts with Anatomy, Hierarchy and Placement. From Vibe: an Accessibility section and "Use cases". From Canvas Kit: an Accessibility Requirements table. From Amsterdam: "How to write" and the token table. From GOV.UK: closing sections for "Research on this component", "Recent changes" and "Help improve this component" ([Circuit Button.mdx](https://github.com/sumup-oss/circuit-ui/blob/HEAD/packages/circuit-ui/components/Button/Button.mdx); [Grafana Button.mdx](https://github.com/grafana/grafana/blob/HEAD/packages/grafana-ui/src/components/Button/Button.mdx); [Vibe Button.mdx](https://github.com/mondaycom/vibe/blob/HEAD/packages/docs/src/pages/components/Button/Button.mdx); [Canvas Kit Button.mdx](https://github.com/Workday/canvas-kit/blob/HEAD/modules/react/button/stories/button/Button.mdx); [GOV.UK Button](https://design-system.service.gov.uk/components/button/)). Orientation comes before components. Grafana opens with Intro, Design Principles, Accessibility and Voice and Tone, and its Intro explains how to use Storybook itself ([Grafana Intro.mdx](https://github.com/grafana/grafana/blob/HEAD/packages/grafana-ui/src/Intro.mdx)). Carbon gives designers and developers separate places to start ([Carbon designing](https://carbondesignsystem.com/designing/get-started/)).

Sidebars read best when grouped by job (inputs, navigation, overlays, tables) with a separate area for experimental and deprecated items. They read worst as a flat A–Z list or with internal and test folders in public view, as Canvas Kit's 169 testing entries and Vibe's internal blocks show ([Canvas Kit index.json](https://workday.github.io/canvas-kit/index.json); [Vibe index.json](https://vibe.monday.com/index.json)). Labelling patterns and pages by audience maps onto Go Vocal's front office and back office. Amsterdam separates public pages from internal ones and explains how to read a page's anatomy ([Amsterdam page anatomy](https://amsterdam.github.io/design-system/?path=/docs/pages-guidelines-reading-the-anatomy--docs)). Bitwarden shows that full product screens belong beside the primitives, where they also work as visual tests ([Bitwarden Kitchen Sink](https://components.bitwarden.com/?path=/docs/documentation-kitchen-sink--docs)). Here govocal-ds's 27 patterns and demo back office already put it in a minority. Only **56% of systems document UX patterns and 34% offer onboarding material**, and complete documentation makes high trust **20% more likely** ([zeroheight 2026](https://report.zeroheight.com/2026)). One addition would help the designer most: a "which token for which job" table on every foundation page, which no generated swatch grid answers.

### An interface layer agents cannot misread

The long-term goal of letting more roles build product with AI is already practice among peers, and they publish it openly. Amsterdam runs a public MCP endpoint (Model Context Protocol, a standard way for AI tools to query a source). Its "AI assistance" page warns that "without this context, an assistant guesses: it writes generic HTML, invents property names" ([Amsterdam AI assistance](https://github.com/Amsterdam/design-system/blob/main/storybook/src/docs/guidelines/ai-assistance.docs.mdx)). Canvas Kit documents an MCP server and ships Agent Skills files, and Vibe exposes MCP tools for component metadata, accessibility and tokens ([Canvas Kit MCP](https://workday.github.io/canvas-kit/?path=/docs/ai-for-llms-mcp-docs--docs); [Vibe MCP](https://vibe.monday.com/?path=/docs/mcp--docs)). The measured gains are real but reported by vendors. Storybook's own benchmark on one library found **12.8% better component reuse, 2.76× faster generation and 27% fewer tokens** with its MCP, without disclosing the model or sample size ([Storybook MCP for React](https://storybook.js.org/blog/storybook-mcp-for-react/)). Atlassian reports a **52% accuracy improvement** from its context engine ([Atlassian context engine](https://www.atlassian.com/blog/ai-at-work/atlassian-design-system-building-the-context-engine-for-the-ai-era)). It also found that on one task a plain DESIGN.md file used 7.21M tokens against 3.75M for its MCP, because agents recreated components instead of importing them ([Atlassian DESIGN.md](https://www.atlassian.com/blog/how-we-build/atlassians-design-md-is-here-what-we-learned-testing-portable-design-context-in-practice)).

The failure to design out is a thin manifest. One team's agent nearly rebuilt components that already existed. The prop types came back empty, and the guidance on when to use Select, Segmented or Toggle sat in a Docs tab the manifest never reads ([rachel.fyi](https://rachel.fyi/posts/storybook-mcp-reads-your-manifest-not-your-docs-tab)). Two facts bear directly on govocal-ds. Storybook's MCP runs on the development server, not from a static build such as GitHub Pages, and its manifest feature is still in preview ([Storybook MCP](https://storybook.js.org/docs/ai/mcp/overview); [Storybook manifests](https://storybook.js.org/docs/ai/manifests)). Publishing a reachable endpoint for the Storybook is the Storybook's own decision; wiring it into product repositories is the developers'.

### Evidence instead of claims

The developers' skepticism matches the industry data. In Stack Overflow's 2025 survey, **46% of developers distrust AI accuracy, experienced developers report 2.6% high trust, and 75.3% turn to a human** when they don't trust an AI answer ([Stack Overflow 2025](https://survey.stackoverflow.co/2025/ai); [press release](https://stackoverflow.co/company/press/archive/stack-overflow-2025-developer-survey/)). DORA 2025 found that AI raises throughput but lowers stability "without robust control systems, like strong automated testing" ([DORA 2025](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)). Review alone does not scale either: under heavy AI use, median time in review rose **441.5%** in Faros's telemetry ([Faros](https://www.faros.ai/blog/ai-code-quality-senior-engineer-review-burden)).

What persuades, then, is a set of checks that give the same answer every time and that a developer can rerun with one command. That set covers type checks, a token-existence check and a raw-value lint, story smoke tests, interaction tests, and visual baselines in both writing directions and every theme. The checks should be visible in the Storybook itself, the way Designsystemet tags all 377 entries for accessibility tests and Bitwarden runs 102 scripted stories ([Designsystemet index.json](https://storybook.designsystemet.no/index.json); [Bitwarden index.json](https://components.bitwarden.com/index.json)). Two additions that no exemplar publishes would put govocal-ds ahead. One is a provenance note per component, saying what agents built, what a person reviewed and where the agents stopped; the agent-pipeline write-up calls naming that stopping point "the most honest thing an agent system can do" ([kaelig.fr](https://www.kaelig.fr/design-system-components-with-ai-agent-teams/)). The other is a "break it" demonstration in which a broken token, label, prop and visual each turn a check red. Status and change records complete the evidence. Circuit defines what each lifecycle stage promises. B.C. Gov keeps its changelog inside Storybook ([B.C. changelog](https://designsystem.gov.bc.ca/react-components/?path=/docs/changelog--docs)). A decision log, with each entry tagged design, developer or joint, shows which calls design has made and which it leaves open.

## Developers keep four calls, and the Storybook should prepare each one

The ownership line follows a long-standing split in front-end work. One side decides "the look and feel of a button"; the other decides "what happens when that button is clicked", meaning business logic, routing, state management and caching ([Brad Frost](https://bradfrost.com/blog/post/front-of-the-front-end-and-back-of-the-front-end-web-development/), 2019, still the reference). A 2026 proposal for designers working in a code repository draws three zones. In the first, designers make changes and developers review them: layout, copy, visual values, icons and the design system. In the second, developers own and designers propose: stores, API calls, routing, auth and CI. In the third, the two decide together ([Designed by Thanh](https://designedbythanh.substack.com/p/designers-in-the-repo-who-owns-what)). In govocal-ds's model, the components and their API sit in design's zone, and four calls stay with developers. The audit does not grade developers' work. It grades whether the Storybook gives them what they need to decide, without deciding for them.

The first call is the **base library**. React Aria may stay or go. The Storybook prepares that decision by saying on every page where behaviour comes from, as B.C. Gov does. It should also keep a table of what is tied to React Aria and what survives, and keep its role-based tests ready to serve as acceptance tests for a rebuild. The second call is **consumption and delivery**: whether the components ship as a versioned package, how versions are pinned and upgraded, how the CSS enters the developers' build, server rendering, bundle budgets, and how long the components coexist with the platform's current styling. The Storybook can publish facts to inform that call, such as size per component, CSS layering, the absence of runtime CSS-in-JS and server-rendering behaviour. Then it should list the options. One relevant fact for that conversation: Primer moved off what it called the "end-of-life library styled-components" to static CSS on CSS variables, citing smaller bundles and faster rendering, and kept a bridge package for consumers still on it ([Primer v38](https://github.com/primer/react/discussions/7086); [ADR-022](https://github.com/primer/react/blob/main/contributor-docs/adrs/adr-022-styled-react.md)). Whether that applies to Go Vocal is the developers' call.

The third call is the **integration seams**, where design's API meets the developers' application. Components take all their copy as props, so the translation library stays the developers' choice. They pass references and form properties through to the real input, so the developers' form library can wire them. They accept a router link. They expose loading, empty and error states that the developers' data layer triggers. Primer's audit found that props not passed through to the root block test hooks and accessibility attributes ([Primer #8384](https://github.com/primer/react/issues/8384)), so the audit should check this in the stories, using stand-ins for router, form and translation code. The fourth call is the **terms of adoption**: whether to adopt, which screens come first, at what pace, and with which gates. The data explains why this call must stay theirs. Lack of a company mandate is the top barrier to adoption, cited by **73%**, and satisfaction with how organisations secure buy-in fell **from 42% to 32%** ([zeroheight 2026](https://report.zeroheight.com/2026)). A proposal without a mandate has three levers the same survey ranks highly: component completeness, communication and documentation.

The Storybook should therefore carry three pages. The first is an ownership-boundary page. The second is an open-questions list per component, shaped like Carbon's public RFCs: what design decided and why, the proposed API, and the questions only engineering can answer ([Carbon RFCs](https://github.com/carbon-design-system/rfcs)). The third names the later options plainly: a blocking accessibility gate for the front office, a lint pack the developers' apps could switch on, review rights over the API diff, and wiring their agents to the MCP. Developers who hold these calls are not being handed a mandate, which is the failure practitioners describe as "designers telling devs" what to do ([Headway](https://www.headway.io/blog/the-design-system-adoption-problem-is-older-than-ai)).

## A 100-point rubric: 85 for design's work, 15 for developer readiness

No published framework scores a Storybook from 0 to 100. The maturity models avoid a single weighted number on purpose and show profiles instead: NN/G rates six dimensions from 1 to 5 ([NN/G](https://www.nngroup.com/articles/design-system-maturity/)), and designsystems.one states that "the lowest dimension caps the system" ([designsystems.one](https://www.designsystems.one/foundations/maturity-model)). The machine-checkable scorecards do weight and add up. Open Design System Bench produces a 0–100 AI-readiness score and gates on the worst dimension rather than the average ([ODSB](https://github.com/christophhdesign/open-design-system-bench)). The rubric below takes from both. Each criterion is scored 1 (absent), 3 (functional) or 5 (exceptional), with 2 and 4 in between, using NN/G's labels. Every score cites its evidence (a story ID, file path, URL or command output), the way the W3C accessibility maturity model requires "proof points" ([W3C AMM](https://www.w3.org/TR/maturity-model/)). A dimension earns (average level − 1) ÷ 4 × its weight, so an empty dimension earns nothing and a fully evidenced one earns everything. Criteria that don't apply, such as Figma checks when no Figma library is kept, drop out of the average. The profile of levels is reported beside the total, so one number cannot hide an uneven system. The weights lean towards what the two stakeholders named: tokens and language for the developers, the bible for the designer. Accessibility counts in three places: behaviour specs (D4), page guidance (D5) and its own reporting dimension (D6).

Two gates stop the total from hiding a hole. First, if any design-owned dimension averages below level 2, the total is capped at 60, following the "lowest dimension caps the system" rule. Second, a red line: a single undefined `--gv-*` reference, or an unlisted raw value in component CSS, caps the total at 60 until it is fixed. That makes "cemented in tokens" a pass/fail property rather than a trend, which is the test the developers asked for. Accessibility carries no gate, in line with the project's decision. Developer-owned dimensions carry none either, because they grade preparation, not maturity.

Before govocal-ds is scored, the six panel Storybooks should be scored on public evidence only. Criteria tied to govocal-ds's own context, such as the city boundary or the civic glossary, are marked as not applicable for them. That shows what 60 and 85 mean in practice, and expectations should stay modest. The best public system on Open Design System Bench scored **63.4**, and its author concluded "nobody is AI-native yet" ([ODSB article](https://christophhellmuth.com/open-design-system-bench/)). In the agent-readiness index of 37 systems, the top score is 4 out of 5 and **19 systems score zero** ([designsystems.one AI index](https://www.designsystems.one/ai-ready/systems)). Panel members will lose points on provenance and agent evaluations because none of them publishes either, which is exactly where govocal-ds can lead. The weights, the 60 cap and the readiness scale are proposals. No source validates weights against adoption outcomes, so they should be tuned once after the panel is scored and then fixed. Adoption, developer trust and team capacity stay out of the score. NN/G's model rates those through four to eight insiders, not public evidence. Most of what the rubric needs is readable from outside: `index.json` for stories, docs and tags; `project.json` for version and add-ons; the components manifest for props; an axe sweep over every story; and Terrazzo, Stylelint and Vale over the repository. One gap remains: nobody has yet confirmed that a static GitHub Pages build serves the manifest files that Storybook 10.6 previews.

## Conclusion

The question the developers raise, whether an AI-built system can be strong, is not really about AI. Amsterdam, Canvas Kit, Vibe and Singapore already publish their agent tooling as ordinary documentation, so being agent-built is becoming normal practice. What the field lacks is proof. No exemplar publishes a token-coverage figure, a per-component provenance note or a repeatable agent evaluation. govocal-ds can make up for having no mandate by publishing the evidence the established systems never had to show. Its most persuasive move is not a claim of quality but a demonstration that breaking a token, a label, a prop or a picture turns a check red.

The model itself is new: designers own agent-built component code that developers import, on a base library the developers may replace. The first audit is therefore a test of the model as well as of the Storybook. Its most useful output is the profile, not the total. A Storybook that scores high on tokens, language and the bible, but low on developer readiness, would be strong work that is not yet aligned with its developers. That outcome is cheaper to fix than the reverse, and the rubric is built to show which one it is.
