# Storybook as the designer's bible: docs that teach, designer ownership, and consistent language (benchmark for the govocal-ds audit)

Research date: 29 Oct 2026. Sources are 2025–2026 unless marked **[background]**. Where a claim comes only from a search-engine summary (page not fetched or fetch failed), it is marked **[snippet]**: treat it as lower confidence.

**Ownership tags.** Developers who import the components make the strategic implementation calls: the component library (React Aria may be dropped), the styling technology, packaging and migration. Every practice below is tagged:
- **[DESIGN-OWNED]**: valid whatever the implementation (docs, usage guidance, naming of concepts, content rules, states, anatomy, behaviour outcomes, token names and values, Figma hygiene, sign-off).
- **[DEV-OWNED]**: depends on the code stack (library, prop spelling, build/CI, packaging, codegen, manifests generated from TypeScript, Code Connect mappings).
- **[SPLIT]**: design owns the *what* and devs own the *how*. Each one says which half is which.

Survey statistics are context, not practices, and are untagged.

## 1. Docs anatomy: what the best per-component pages contain, and where they live (inside Storybook vs a separate docs site)

### Takeaway
The leading systems converge on the same per-component anatomy: a one-line purpose, when to use and when not to, live examples of variants and states, do/don't visuals, anatomy, content (copy) guidance, accessibility, API/props, related components, status, and a changelog. Almost all of it is DESIGN-OWNED and implementation-agnostic. Only the props/API table and the code snippets are DEV-OWNED. Storybook 10.6 has the blocks to hold both layers in MDX. The best systems either split guidance onto a curated site with the API in Storybook, or keep both in one Storybook with custom blocks (monday.com Vibe).

### Cited Findings
**Anatomy exemplars**
- **[DESIGN-OWNED except the API section, which is DEV-OWNED]** GitHub Primer gives every component page three tabs. **Overview** has a summary, implementation info (React, Rails, Figma), usage examples, variants (style, size, layout), the API, and related links to patterns, accessibility and related components. **Guidelines** has best practices, when and when not to use, do/don't visuals, common pitfalls, an anatomy diagram, content and copywriting guidance, layout/responsive notes and behaviour. **Accessibility** has keyboard, touch targets, assistive technology and known issues, structured as Presentation / Adaptability / Interaction / Assistive technology. Primer also defines a "minimum-viable documentation" floor: a brief description, implementation links, usage guidance with visuals, and cross-references — [Primer: Contribute documentation](https://primer.style/contribute/documentation). The Guidelines and Accessibility tabs have one copy each, shared by several implementations (React, Rails, Figma), so the guidance is written to stay valid across stacks.
- **[DESIGN-OWNED guidance; DEV-OWNED code blocks]** On GOV.UK, the Button page sections run in this order: When to use this component → How it works → Research on this component → Recent changes → Help improve this component → Need help? Every variant (default, start, secondary, warning, inverse, disabled, grouped, prevent double-click) has a live example plus **plain HTML** and Nunjucks code. The page links to the component's GitHub discussion so people can share research or propose changes. The last change was logged in Jul 2026 (Frontend v6.4.0) — [GOV.UK Design System: Button](https://design-system.service.gov.uk/components/button/)
- **[DESIGN-OWNED]** The GOV.UK Button page also carries copy guidance: exact button labels per situation ("Start now", "Sign in", "Continue" when data isn't saved, "Save and continue" when it is, "Save and come back later", "Add another", "Confirm and send", "Sign out"), sentence case, and labels that describe the action — [GOV.UK Design System: Button](https://design-system.service.gov.uk/components/button/)
- **[SPLIT: Components' "props/API" and the contribution model's versioning are DEV-OWNED; purpose, variants/states, accessibility, tokens' intent, usage examples and do/don't are DESIGN-OWNED]** The Storybook blog (9 Sep 2026) names five core doc elements. **Components** must answer "how do I use this?" within one minute: purpose, props/API, variants/states, accessibility and live instances. Then **Tokens** with documented intent, **Usage examples** (how components combine into forms, navigation, tables), **Do's and Don'ts** as visual side-by-side comparisons, and a **Contribution model** (proposing, acceptance criteria, review, versioning). It cites Spectrum, Primer and Carbon as exemplars — [Storybook blog: How to document your design system](https://storybook.js.org/blog/how-to-document-your-design-system-best-practices-tools/)
- **[DESIGN-OWNED]** The same post says to give designers principles, brand, usage guidance and visual references, and developers APIs, props, code examples and interactive references: "Keep content clear and useful for both audiences. Where their needs diverge… make both easy to find and label clearly" — [Storybook blog](https://storybook.js.org/blog/how-to-document-your-design-system-best-practices-tools/)
- **[SPLIT: state and behaviour specs are DESIGN-OWNED; the stories and the Storybook/website docs pipeline are DEV-OWNED]** Carbon's component checklist asks for "Documentation: long-form docs in Storybook and website" and "Storybook: default and playground stories". Its design specs must document hover, focus, disabled, error and warning states, plus responsive, overflow and scroll behaviour — [Carbon: Component checklist](https://www.carbondesignsystem.com/getting-started/contributing/component-checklist)
- **[DESIGN-OWNED] [background]** EightShapes lists what a component spec contains: Anatomy, Properties, Layout and spacing, Behavior, Accessibility, Motion, Component tokens, Version history. Anatomy "establishes the hierarchy of elements and groups that map to web markup, object composition, and Figma layers", and annotation visuals need their own colour (often orange) so they aren't mistaken for the component — [EightShapes: Component Specifications](https://medium.com/eightshapes-llc/component-specifications-1492ca4c94c); [EightShapes Specs Figma plugin](https://medium.com/eightshapes-llc/the-eightshapes-specs-figma-plugin-2892f21adc96) (automates the Anatomy, Props and Layout & spacing frames in Figma, which makes it a design-side spec tool)
- **[DESIGN-OWNED status labels]** **[snippet]** Twilio Paste pages show a status (production/beta/alpha), a documentation "peer review" status (many marked "Pending"), owner attribution and a per-component accessibility statement. Paste says it follows WCAG 2.1 AA and the W3C ARIA authoring practices — [Paste components overview](https://paste.twilio.design/layout); [Paste Status Badge](https://paste.twilio.design/components/status-badge). Caveat: on 29 Oct 2026, fetching `paste.twilio.design/components/pagination` returned a 301 to `github.com/twilio-labs/paste`, so the docs site may have been retired or moved. Verify before using it as a live exemplar.

**Inside Storybook (MDX, doc blocks, autodocs)**
- **[SPLIT: Description/Title/Subtitle prose, ColorPalette/Typeset/IconGallery content and MDX guidance are DESIGN-OWNED; ArgTypes/Controls tables and Source snippets reflect code and are DEV-OWNED]** Storybook 10.6 ships these doc blocks: Meta, Title, Subtitle, Description, Primary, Controls, ArgTypes, Stories, Story, Canvas, Source, ColorPalette, Typeset, IconGallery, Markdown, Unstyled and TableOfContents, plus the `useOf` hook for custom blocks. **Description** "displays the description for a component, story, or meta obtained from their respective JSDoc comments". The autodocs template can be replaced with your own arrangement of blocks — [Storybook docs: Doc blocks](https://storybook.js.org/docs/writing-docs/doc-blocks)
- **[DEV-OWNED mechanism]** Autodocs builds a page per component from story metadata (props, variants, controls), which MDX extends with prose — [Storybook docs: Autodocs](https://storybook.js.org/docs/writing-docs/autodocs); [Storybook docs: MDX](https://storybook.js.org/docs/writing-docs/mdx)
- **[DESIGN-OWNED presentation]** monday.com's Vibe keeps its whole documentation in Storybook (`style.monday.com`). It is themed to the brand, with colour tokens, spacing and motion guidelines beside the interactive examples — [Supernova: 8 Storybook examples from real design systems (24 Jun 2025)](https://www.supernova.io/blog/top-storybook-documentation-examples-and-the-lessons-you-can-learn)
- **[DEV-OWNED package; DESIGN-OWNED content]** Vibe publishes a `storybook-blocks` package of custom doc components, mapped once in `preview.js` for use in MDX — [Vibe storybook-blocks README](https://github.com/mondaycom/vibe/blob/master/packages/storybook-blocks/README.md). (The README does not list the individual blocks, so I could not verify block names such as do/don't or related components.)
- More "inside Storybook" exemplars from the same 2025 roundup: Clarity Core (theme toggles), BBC iPlayer (Markdown notes plus compact colour/type/motion style guides, Storybook as a "living artefact"), Grommet (viewport + theming), WordPress Gutenberg (stories as "the contract that keeps community contributions on spec"), and The Guardian (a "Development Kitchen" namespace that keeps experimental work apart from production) — [Supernova (Jun 2025)](https://www.supernova.io/blog/top-storybook-documentation-examples-and-the-lessons-you-can-learn)

**Separate docs site vs Storybook**
- The Storybook blog's tool comparison: Storybook is developer-facing and code-synchronised, with native live components. zeroheight is designer-facing WYSIWYG and embeds Storybook. Knapsack is a unified workspace with live components. Supernova does design-to-code token pipelines. Frontify is brand-led. GitBook is general docs — [Storybook blog](https://storybook.js.org/blog/how-to-document-your-design-system-best-practices-tools/)
- The tools teams use for documentation (zeroheight 2026, n=147): Figma 69%, Storybook 61%, zeroheight 32%, Confluence 18%, custom 16%, Supernova 7% — [zeroheight Design Systems Report 2026](https://report.zeroheight.com/2026)
- **[DESIGN-OWNED guidance site; DEV-OWNED implementations]** Adobe Spectrum presents design guidance at spectrum.adobe.com, with dedicated areas for the React and Web Components implementations (in beta) and iOS/Android "coming soon". Component pages carry an interactive playground of props and attributes — [Spectrum](https://spectrum.adobe.com/). Spectrum CSS is a CSS-only implementation that "should only be used by implementations of Spectrum", next to React Spectrum and Spectrum Web Components (`sp-*` elements, the "same design language as React Spectrum") — [Spectrum CSS README](https://github.com/adobe/spectrum-css/blob/main/README.md); [UICentral: Spectrum Web Components](https://uicentral.fyi/component-libraries/spectrum-web-components) **[snippet]**

### Inferences
- **The govocal-ds page template should mark its two layers explicitly.** The spec layer (DESIGN-OWNED) is purpose, when and when not to use, anatomy, variants and states as concepts, behaviour, content, accessibility outcomes, tokens and do/don't. It should never name React Aria or code syntax, so it survives a library change. The implementation layer (DEV-OWNED) is the ArgTypes/Controls table, Source snippets and install notes, and it can be swapped. Primer's one-guidelines-tab-for-React-Rails-and-Figma and Spectrum's guidance-above-implementations are the precedents.
- govocal-ds already puts a doc comment on every component, and the Description block reads exactly those JSDoc comments. But JSDoc sits *in the code file*, which developers may replace. If the purpose sentence is DESIGN-OWNED, a copy of it should also live in MDX or a design-owned data file, so it survives a rewrite of the component. The audit can check the sentence exists in both and matches.
- GOV.UK shows **plain HTML** for every example, next to its framework macro. That makes the HTML (structure plus classes plus ARIA) a framework-neutral reference any stack can reproduce. A design proposal can do the same: show the rendered HTML/ARIA outcome, not only the React source.

### Gaps
- I could not verify the exact names of Vibe's custom blocks (the README doesn't list them, and the Storybook SPA didn't render for the fetcher).
- I did not fetch the Atlassian, Fluent or Polaris component pages for their exact section order, nor the Spectrum component page for how it lists implementations. Primer, GOV.UK and Carbon stand in as the verified anatomy exemplars.
- Whether Paste's docs site is still live is unresolved (see the redirect above).

## 2. Teaching structure: principles → foundations → components → patterns → templates, and onboarding

### Takeaway
Nearly every system ships foundations and components. Patterns and copy guidance are far less common, and onboarding material is offered by only about a third. The best systems give designers and developers separate getting-started roads (Carbon, Atlassian), and GOV.UK ties each component to research and a public discussion. All of the teaching structure is DESIGN-OWNED except the developer setup pages.

### Cited Findings
- What design systems include (zeroheight 2026): foundations 93%, documentation 92%, design libraries 91%, tokens 86%, code libraries 78%, accessibility guidelines 59%, **UX patterns 56%**, **UX copy guidelines 38%**, brand 37%, illustrations 33% — [zeroheight 2026](https://report.zeroheight.com/2026)
- What teams provide to users: documentation 90%, 1-1 consultation 71%, workshops/training 40%, **onboarding materials 34%**, videos 19%, chatbots 13% — [zeroheight 2026](https://report.zeroheight.com/2026)
- **[DESIGN-OWNED "Designing" road; DEV-OWNED "Developing" road]** Carbon splits "Designing → Get started" (principles, Figma design kits that update automatically when the libraries change) from "Developing → Overview" (tutorials, installation, framework setup; React first, Web Components official, community Angular/Vue/Svelte). It is one guidance site over several implementations — [Carbon: Designing / Get started](https://carbondesignsystem.com/designing/get-started/); [Carbon: Developing overview](https://www.carbondesignsystem.com/getting-started/developing/overview) **[snippet-level for the details]**
- **[DESIGN-OWNED]** Atlassian has a get-started page for content designers as well as foundations for content (voice and tone, inclusive writing, language and grammar) — [Atlassian: Get started, content design](https://atlassian.design/get-started/content-design); [Atlassian: Content foundations](https://atlassian.design/foundations/content) **[snippet]**
- **[DESIGN-OWNED]** GOV.UK component pages tell newcomers why a component looks the way it does ("Research on this component") and how to take part ("Help improve this component", which links to the GitHub discussion) — [GOV.UK Button](https://design-system.service.gov.uk/components/button/)
- **[DESIGN-OWNED labelling; DEV-OWNED Storybook config]** The Guardian's Storybook keeps a separate "Development Kitchen" namespace so newcomers can see what is experimental and what is production-ready — [Supernova (Jun 2025)](https://www.supernova.io/blog/top-storybook-documentation-examples-and-the-lessons-you-can-learn)
- The Storybook blog lists "Burying practical usage information beneath theoretical content" as a failure mode, so the teaching order must not push "how do I use this" below the fold — [Storybook blog](https://storybook.js.org/blog/how-to-document-your-design-system-best-practices-tools/)

### Inferences
- The govocal-ds sections (Overview, Foundations, Components, Patterns) already match the common spine. Patterns and UX copy are where most systems are thin (56% and 38%), and both are DESIGN-OWNED, so they are where a design-led proposal can beat the industry median without touching any developer decision.
- Because govocal-ds is a proposal, the developer "start here" page should read as an *offer*: what design guarantees (tokens, states, content, behaviour), what it suggests (a reference implementation), and what developers decide. That frames the Storybook as "making your life simpler", not as a mandate.

### Gaps
- I found no 2025–2026 source with data on whether separate designer and developer getting-started paths improve adoption.
- "Templates" as a teaching layer: I did not verify which exemplar systems publish page templates and how.

## 3. The designer ↔ developer bridge, and designer ownership and governance

### Takeaway
The bridge tooling is mature but scattered, and mostly DEV-OWNED to set up. The designs addon puts Figma in Storybook. Storybook Connect puts stories in Figma (but needs Chromatic). Code Connect maps real code into Figma Dev Mode, and its Storybook parser is now legacy. Chromatic UI Review gives designers a formal sign-off on visual changes. The *acts* done through those tools — linking Figma, signing off visuals, setting status — are DESIGN-OWNED. 2025–2026 writing shows designers opening pull requests directly, governed by an explicit split of who owns what plus mandatory developer review.

### Cited Findings
**Tools**
- **[SPLIT: installing the addon is DEV-OWNED; adding and keeping the Figma links is DESIGN-OWNED]** `@storybook/addon-designs` embeds Figma files and prototypes (Figma Live Embeds) in a Storybook panel and respects each viewer's Figma permissions. **[DESIGN-OWNED once set up]** The **Storybook Connect** Figma plugin links stories to Figma components and shows "view story" on every instance, in Design Mode and Dev Mode. It **requires the Storybook to be published on Chromatic**, Figma edit rights and Chromatic collaborator status — [Figma Help: Storybook and Figma](https://help.figma.com/hc/en-us/articles/360045003494-Storybook-and-Figma)
- **[DEV-OWNED]** Figma Code Connect can read Storybook stories (`parameters.design` with `type: 'figma'`, `url`, `examples`, plus `figma.string/boolean/enum` prop mapping and variant restrictions). But it is **React only**, and "framework-specific parsers, including Storybook, no longer receive updates; template files are the recommended approach" — [Figma developer docs: Code Connect + Storybook](https://developers.figma.com/docs/code-connect/storybook/)
- Schema 2025 (28 Oct 2025) announced:
  - **[DEV-OWNED]** A Code Connect UI that links Figma to GitHub repos with AI file suggestions, "no coding necessary".
  - **[SPLIT: the guidelines' content is DESIGN-OWNED; the server and its wiring are DEV-OWNED]** The Figma MCP server became GA, with "guidelines for how AI models should adhere to your design system".
  - **[DESIGN-OWNED]** Slots (early access) let designers add layers inside instances without detaching.
  - **[DESIGN-OWNED]** Extended collections for multi-brand systems.
  - **[DESIGN-OWNED token source; DEV-OWNED consumption]** Variables import/export aligned with the **DTCG 1.0** token spec.
  - **[DESIGN-OWNED]** "Check designs" (early access), an AI linter that suggests the right variables.
  — [Figma blog: Schema 2025 recap](https://www.figma.com/blog/schema-2025-design-systems-recap/)
- **[SPLIT: the designer's sign-off is DESIGN-OWNED; the CI and Chromatic setup are DEV-OWNED]** In Chromatic UI Review you assign designers, PMs and other stakeholders as reviewers on the exact visual changeset of a branch. They comment and request changes, and the Review "Passes" once approvals and checklist items are done. Sign-off shows in the PR and CI — [Chromatic docs: Review](https://www.chromatic.com/docs/storybook/review/); [Chromatic: UI Review](https://www.chromatic.com/features/review)
- **[DEV-OWNED manifest, generated from component code; the descriptions written into it can be DESIGN-OWNED]** The Storybook MCP server (Storybook 10.6, AI features "in preview") has Docs tools (`docs-list`, `docs-show`, `docs-show-story`) that read a generated **components manifest** (off by default, `componentsManifest: true`; React, Angular-Vite and Vue3-Vite only), plus Development and Testing toolsets (`test-run` includes a11y checks). Its agent instructions say: "CRITICAL: Never hallucinate component properties!… you MUST use the MCP tools to check if the property is actually documented", using only props "explicitly documented or shown in example stories" — [Storybook docs: MCP server](https://storybook.js.org/docs/ai/mcp/overview)
- **[DEV-OWNED]** Carbon also offers a "Carbon MCP" that gives AI tools live access to components, tokens, icons, guidance and code — [Carbon home](https://www.carbondesignsystem.com/) **[snippet]**

**Status, lifecycle and design/code parity markers**
- **[DESIGN-OWNED definitions; the "Stable" bar spans both]** Carbon defines four statuses tied to its product lifecycle. **Draft** ("partially complete, ready for validation"), **Preview candidate**, **Preview** ("mostly complete, changes possible"), and **Stable** ("complete across code, kit, docs, design") — [Carbon: Component checklist](https://www.carbondesignsystem.com/getting-started/contributing/component-checklist)
- **[DESIGN-OWNED lifecycle]** NL Design System (the Dutch government's shared system) uses a relay model, the *estafettemodel*: Help Wanted → Community → Candidate → **Hall of Fame**. A Hall of Fame component has been used in production by at least two organisations, tested by developers, designers and end users, and passed an accessibility audit. A feedback phase before it gives the community time to test the Candidate in different house styles — [NL Design System: Estafettemodel](https://nldesignsystem.nl/handboek/estafettemodel/); [Hall of Fame DoD](https://nldesignsystem.nl/handboek/estafettemodel/componenten/hall-of-fame/); [Definition of Done](https://nldesignsystem.nl/componenten/definition-of-done) **[snippet for the details]**
- **[SPLIT: choosing and assigning statuses is DESIGN-OWNED; installing the addon is DEV-OWNED]** Storybook's tag system can carry status. `@etchteam/storybook-addon-status` shows tags such as beta, stable, deprecated and releaseCandidate as sidebar dots or tags, and `storybook-addon-tag-badges` ships preset badges (new, alpha, beta, rc, experimental, deprecated) — [Storybook addon: Status](https://storybook.js.org/addons/@etchteam/storybook-addon-status); [Storybook addon: Tag Badges](https://storybook.js.org/addons/storybook-addon-tag-badges)
- **[DESIGN-OWNED Figma hygiene]** Parity practice (Design System Diaries, 20 Mar 2025). "Keeping Figma component names identical ensures designers and developers are always talking about the same thing". "Design tokens need to match code exactly. If a developer is using primary.default, don't call it Primary/Main in Figma". Use Figma's code-syntax field for tokens. Model optional slots as a boolean (`iconBefore`) plus an instance swap, link Storybook from Figma component descriptions, and name layers after code (e.g. "container") — [Design System Diaries: Close the gap](https://designsystemdiaries.substack.com/p/close-the-gap-how-to-boost-parity)
- **[SPLIT]** GitLab Pajamas tracks "component health evaluation" across implementations and docs (e.g. it found a Rails Badge whose icon didn't change colour with its variant). Docs count as ready "when there are no todos, examples are included, and configuration details are comprehensive" — [GitLab issue: Component health evaluation tracking](https://gitlab.com/gitlab-org/gitlab-services/design.gitlab.com/-/issues/2866) **[snippet]**

**Designers owning the repo (who owns what)**
- **[governance model: it defines the DESIGN-OWNED vs DEV-OWNED zones]** "Designers in the repo: who owns what?" (1 Oct 2026) proposes three zones:
  - **Designer changes, developer reviews**: classes/layout, copy, visual values in the UI package, icons and the design system, responsive behaviour, and the "what/why" of DESIGN.md.
  - **Developer owns, designer proposes**: stores, API calls, async, routing, auth, CI/CD, privacy/security.
  - **Decide together**: e.g. permission UI.

  Governance: the designer's agent checks before every push that tests pass and nothing conflicts, "A human review is mandatory before any merge", and developers mark decisions "Status: live, design to review" for async designer assessment — [Designed by Thanh](https://designedbythanh.substack.com/p/designers-in-the-repo-who-owns-what)
- **[governance]** A small open-source example of designers owning a DS repo through a CODEOWNERS file (a governance PR) — [Socium-Design PR #30](https://github.com/Socium-Design/design_system_angular/pull/30) **[snippet; small project, illustrative only]**
- **[background]** EightShapes on contribution: a system must state the expectations and process for submitting and reviewing code, usually through pull requests — [EightShapes: Contributions to Design Systems](https://medium.com/eightshapes-llc/contributions-to-design-systems-89261a9363d8) **[snippet]**
- zeroheight 2026: 65% of systems let anyone on the product team contribute, 17% only specific people, 14% only the DS team. Just 36% are satisfied with contribution. 21% use designer/engineer secondments. Hybrid design-engineering respondents rose to 8% (3% in 2025). DS teams of 1–10 people run about 1 designer to 2 developers — [zeroheight 2026](https://report.zeroheight.com/2026)

### Inferences
- **Storybook Connect needs Chromatic.** govocal-ds publishes to GitHub Pages, so stories reach Figma only if the Storybook is also published to Chromatic, which is a DEV-OWNED call. Otherwise the DESIGN-OWNED fallback is a Storybook URL in each Figma component description, as Design System Diaries recommends.
- **Code Connect is wholly DEV-OWNED,** and its Storybook parser is legacy and React-only. If developers drop React Aria or change stack, any Code Connect work should be left to them (templates or the Code Connect UI). The design proposal should not build on it.
- **The Storybook MCP manifest is generated from code, so it describes the *current* implementation, not the design spec.** The design-side equivalent is a DESIGN-OWNED spec per component (concept properties, allowed values, states, content slots, behaviour). The audit can compare the manifest against it: a manifest prop with no spec concept is implementation detail or drift, and a spec concept missing from the manifest is an implementation gap.
- For a designer working through an AI agent, the three-zone split plus mandatory developer review transfers most directly. It also gives developers what they need: they keep the merge gate and the whole logic and architecture zone.

### Gaps
- I found no authoritative exemplar of an explicit "Not in Figma" / "design debt" badge on component pages. The search turned up only parity articles and GitLab's health tracking.
- I found no 2025–2026 case study of a designer as sole owner of a production design system, nor any data on how well that works.
- I did not verify Chromatic's current pricing or plan limits for UI Review and Storybook Connect.
- Figma's Config 2025 talks were not reviewed. The Schema 2025 recap was used instead.

## 4. Language consistency: component names, prop conventions, glossaries, voice and tone, UI copy, inclusive language, i18n

### Takeaway
Consistent language works on three layers. **Component names and concept vocabulary** (DESIGN-OWNED): follow the cross-system consensus (component.gallery, Open UI) and record aliases. **Prop spelling in code** (DEV-OWNED): conventions like `isDisabled`/`onPress` come from React Aria and would leave with it, so the design side should own the *concept* vocabulary (emphasis, tone, size scale, state names) and let developers own the code spelling. **UI copy** (DESIGN-OWNED): a voice and tone page, a word list or A–Z, and per-component label rules. Industry-wide, copy guidance is the least covered and least satisfying area (38% include it, 21% satisfied).

### Cited Findings
**Component names (DESIGN-OWNED)**
- **[DESIGN-OWNED]** component.gallery catalogues 60 components across 95 design systems (2,671 examples). It gives each component a consensus name and lists aliases underneath, e.g. Accordion = "Collapse, Collapsible sections, Details, Disclosure, Expandable". It also records each system's tech stack, tone-of-voice guidelines, code, accessibility and open-source status — [component.gallery](https://component.gallery/)
- **[DESIGN-OWNED]** Open UI "standardize[s] names, anatomies and behaviors based on common patterns in design systems and component libraries". Each component gets a research page (anatomy, states, behaviours, names across systems) before any proposal, and a Component Name Matrix maps what each system calls the same thing — [Open UI: Working mode](https://open-ui.org/working-mode/); [Open UI: Adding a design system](https://open-ui.org/design-system-analysis-guide/)
- **[DESIGN-OWNED]** Primer's writing rules: PascalCase component names, introduced directly ("ActionMenu is…", not "An ActionMenu is…") — [Primer: Contribute documentation](https://primer.style/contribute/documentation)

**Prop and API conventions (DEV-OWNED spelling; DESIGN-OWNED concepts)**
- **[DEV-OWNED, library-specific]** React Aria / React Spectrum use `onPress` rather than `onClick` because it "behaves the same for mouse, touch, keyboard and screen readers". `onClick` survives only as a compatibility alias, and `onPress` receives a PressEvent carrying the pointer type — [React Aria: usePress](https://react-spectrum.adobe.com/react-aria/usePress.html); **[background, 2020]** [Building a Button Part 1: Press Events](https://react-spectrum.adobe.com/blog/building-a-button-part-1.html)
- **[DEV-OWNED, library-specific]** React Aria components expect `onPress`, `isDisabled`, `isSelected` and `isOpen` instead of the DOM habits — [shadcn.io React Aria rules (aggregator)](https://www.shadcn.io/prompts/react-aria) **[aggregator; consistent with React Aria docs]**
- **[DEV-OWNED spelling]** Common library-wide conventions: camelCase props; booleans with `is`/`has` (`isDisabled`, `isLoading`, `hasError`); events with `on`; one size scale used everywhere (not `size="small"` in one place and `size="compact"` in another); props named for intent, not appearance (`variant="primary"`, not `variant="blue"`) — [designsystems.one: Naming conventions, the API of the system](https://www.designsystems.one/foundations/naming-conventions) **[snippet]**. The last two rules (one scale, intent over appearance) are **DESIGN-OWNED concepts** that hold in any stack.
- **[DESIGN-OWNED concept vocabulary]** One open-source system's 2026 API-consistency PR codifies: "variant = visual shape/emphasis, tone = semantic color, size = scale, status = data state only" — [bridger-design-system PR #75](https://github.com/bridger-kr/bridger-design-system/pull/75) **[snippet; small project; the attribution of this exact wording to this PR rather than designsystems.one was not verified]**

## 6. Failure modes of design-system docs, and how leading teams prevent them

### Takeaway
Docs fail when they are treated as a one-off project, when nobody owns them, when they are split across tools, and when Figma and code drift apart. Leading teams prevent this with a named owner (DESIGN-OWNED for guidance), a definition of done that includes docs (Carbon, NL DS), docs generated from code where possible (DEV-OWNED), visual review gates (SPLIT), parity-by-naming (DESIGN-OWNED in Figma), and public statuses. For a proposal, there is one more failure mode: guidance written *about* one implementation goes stale the day developers pick another (see section 7).

### Cited Findings
- The Storybook blog's failure modes: the "one-time project mentality" ("Documentation needs an owner, a process, and ideally automation that removes the maintenance chore entirely"), practical usage buried under theory, and docs fragmented across disconnected tools — [Storybook blog (Sep 2026)](https://storybook.js.org/blog/how-to-document-your-design-system-best-practices-tools/)
- Stale docs erode trust in all of them: once teams notice inaccuracies, "they stop trusting all of it". The biggest reason docs go stale is that nobody owns the updates — [Magic Patterns: Design system documentation](https://www.magicpatterns.com/blog/design-system-documentation); [Magic Patterns: Design system maintenance](https://www.magicpatterns.com/blog/design-system-maintenance) **[snippet]**
- Variant explosion: accumulated variants, sizes and legacy flags create "different components under the same name". 4 variants × 3 sizes = 12 combinations, and adding icon position, loading and disabled reaches 144 — [Steve Kinney: Maintaining a design system at scale](https://stevekinney.com/courses/enterprise-ui/maintaining-a-design-system) / [Magic Patterns: Enterprise design systems](https://www.magicpatterns.com/blog/enterprise-design-systems) **[snippet; which of the two made the 144 calculation was not verified]**. **[DESIGN-OWNED prevention]**: the variant set is a design decision.
- Mismatched Figma libraries and code are "the default outcome when a design system lacks a maintenance strategy" — [Magic Patterns: Maintenance](https://www.magicpatterns.com/blog/design-system-maintenance) **[snippet]**
- Docs that only one discipline reads: designers fall back to Figma because "it's faster" — [zeroheight 2026](https://report.zeroheight.com/2026)
- **[SPLIT definition of done]** Carbon's "Stable" requires completeness "across code, kit, docs, design", one visual regression test per default story, Equal Access checks, and manual JAWS, VoiceOver and NVDA testing — [Carbon checklist](https://www.carbondesignsystem.com/getting-started/contributing/component-checklist). **[DESIGN-OWNED lifecycle]** NL DS's Hall of Fame requires production use in 2+ organisations and an accessibility audit — [NL DS Hall of Fame](https://nldesignsystem.nl/handboek/estafettemodel/componenten/hall-of-fame/)
- **[SPLIT]** Stories as contract: Gutenberg's stories "keep community contributions on spec", and The Guardian separates experimental work with a namespace — [Supernova (Jun 2025)](https://www.supernova.io/blog/top-storybook-documentation-examples-and-the-lessons-you-can-learn)
- **[SPLIT]** A review gate: Chromatic UI Review puts the exact visual changeset in front of designers before merge — [Chromatic docs: Review](https://www.chromatic.com/docs/storybook/review/)
- **[DEV-OWNED]** Agents that can't invent props: the Storybook MCP binds agents to the documented manifest — [Storybook MCP](https://storybook.js.org/docs/ai/mcp/overview)

### Inferences
- An AI agent can add a variant in seconds, so drift is fast. The audit should count variants and concept properties per component *in the spec* (DESIGN-OWNED), flag any combination without a story, and flag variants with no Figma counterpart.
- The DECISIONS.md / OPEN-DECISIONS.md pair is a strong guard against "who owns the update?". Each entry should carry an ownership tag (design decision vs dev decision vs joint), so a reader can see at a glance which calls the proposal makes and which it leaves to developers.

### Gaps
- I found no quantitative 2025–2026 study linking specific doc practices (do/don't visuals, anatomy diagrams) to measured adoption. The evidence is practitioner consensus plus zeroheight's correlational trust numbers.

## 7. How design teams own the spec and guidance layer without dictating code, and keep a Storybook honest when its code may be replaced

### Takeaway
Three public systems show the model. NL Design System makes "the HTML structure and design decisions… once" and lets each framework wrap them, with tokens in the DTCG JSON standard. Spectrum keeps design guidance above several implementations (React, Web Components, CSS, native coming). Primer writes one guidelines tab for React, Rails and Figma. The design-side spec stays valid when it is written as **outcomes** rather than code: anatomy and names (Open UI), behaviour and keyboard (W3C APG), states, content, and tokens as DTCG JSON. A Storybook stays honest when its code may change if the stories test outcomes (role-based interaction tests, visual baselines, a11y runs), the code is labelled as a *reference implementation*, and Storybook Composition lets the developers' own Storybook, in whatever stack they choose, plug in beside the design spec.

### Cited Findings
**Spec layer that survives any implementation**
- **[DESIGN-OWNED decisions; DEV-OWNED framework wrappers]** NL Design System: "De HTML structuur en design beslissingen van NL Design System componenten worden één keer gemaakt en kunnen daarna hergebruikt worden in elk framework" ("The HTML structure and design decisions of NL Design System components are made once and can then be reused in every framework"). Its layers are framework-agnostic HTML/CSS components, then framework wrappers (React, Vue, Angular, Web Components, Twig), then a theming layer. "Elke organisatie legt de eigen huisstijl vast met de Design Tokens JSON standaard en maakt deze beschikbaar voor hergebruik in Figma, code, websites en diverse webapplicaties" ("each organisation records its house style with the Design Tokens JSON standard and makes it available for reuse in Figma, code, websites and applications"). The core team owns behaviour and accessibility, and communities contribute framework implementations — [NL Design System: Architecture for developers](https://nldesignsystem.nl/handboek/developer/architectuur/)
- **[DESIGN-OWNED token vocabulary]** NL DS components must use standard design tokens so one component works under every organisation's theme. The Utrecht library is the de facto reference implementation, ported to React, Vue, Angular and web components — [developer.overheid.nl: NL Design System](https://developer.overheid.nl/kennisbank/front-end/design-systems/nl-design-system/); [NL DS: Design token convention](https://nldesignsystem.nl/handboek/developer/design-token-conventie/) **[snippet for the Utrecht detail]**
- **[DESIGN-OWNED guidance; DEV-OWNED implementations]** Spectrum: one design site, with implementation areas for React and Web Components (beta) and iOS/Android coming — [Spectrum](https://spectrum.adobe.com/). Several implementations (Spectrum CSS, React Spectrum, Spectrum Web Components) carry the same design language — [Spectrum CSS README](https://github.com/adobe/spectrum-css/blob/main/README.md) **[snippet]**
- **[DESIGN-OWNED]** Primer's component page lists implementation info for React, Rails and Figma under one Guidelines and one Accessibility tab — [Primer](https://primer.style/contribute/documentation)
- **[DESIGN-OWNED names and anatomy]** Open UI standardises names, anatomies and behaviours from common patterns across design systems, with per-component research pages (anatomy, states, behaviours, names) and a Component Name Matrix. Its approach compares many systems rather than adopting any one framework's — [Open UI: Working mode](https://open-ui.org/working-mode/)
- **[DESIGN-OWNED behaviour spec]** The W3C ARIA Authoring Practices Guide (APG) gives framework-agnostic behaviour per pattern. For Button: Space and Enter activate it. Focus moves into a dialog the button opens, returns to the button when the dialog closes, and stays put for in-context actions. Role `button`, an accessible label, `aria-describedby` for descriptions, `aria-disabled="true"` when unavailable, `aria-pressed` for toggles. The site lists 30+ patterns from Accordion to Window Splitter — [W3C APG: Button pattern](https://www.w3.org/WAI/ARIA/apg/patterns/button/); [W3C APG: Patterns](https://www.w3.org/WAI/ARIA/apg/patterns/)
- **[DESIGN-OWNED anatomy]** **[background]** EightShapes: anatomy maps to "web markup, object composition, and Figma layers", in one vocabulary for all three — [EightShapes: Component Specifications](https://medium.com/eightshapes-llc/component-specifications-1492ca4c94c)
- **[DESIGN-OWNED token source]** Figma variables import/export aligned with the DTCG 1.0 token format (from Nov 2025) — [Figma Schema 2025](https://www.figma.com/blog/schema-2025-design-systems-recap/)
- **[DESIGN-OWNED spec authority]** A stack-agnostic reference repo states the rule plainly. Developers read "Principles and Invariants" first ("what must survive translation into any stack"), take exact values from `tokens.json`, and use the component taxonomy "as a specification of purpose/states/portability — not as implementation instructions". When spec and reference implementation disagree, "the Markdown document is authoritative — a mismatch in the implementation is a bug, not a spec change" — [design-system-reference (GitHub)](https://github.com/leviscjr/design-system-reference) **[snippet; a small project, illustrative of the pattern, not an industry exemplar]**
- **[DESIGN-OWNED references, implementation-neutral]** GOV.UK shows plain HTML next to each Nunjucks macro, so any stack can reproduce the structure — [GOV.UK Button](https://design-system.service.gov.uk/components/button/)

**Keeping a Storybook honest when its code may be replaced**
- **[SPLIT: which behaviours to assert is DESIGN-OWNED; the play-function code is DEV-OWNED or written through the designer's agent]** Storybook 10.6 interaction tests use play functions (simulate clicks and typing, assert the result). Storybook and Testing Library "highly encourage you to query for elements in a way that resembles the way a real person would interact with your UI": ByRole first, then ByLabelText/ByText, and ByTestId "a last resort" — [Storybook docs: Interaction tests](https://storybook.js.org/docs/writing-tests/interaction-testing). (The docs do not claim the tests survive refactors. That follows from querying by role and label rather than DOM structure: see Inferences.)
- **[DEV-OWNED setup; DESIGN-OWNED use]** Storybook Composition shows any Storybook reachable by URL inside another's sidebar, through `refs` in `.storybook/main.ts`. Composed Storybooks can use "any view layer", and the listed use cases include multi-framework integration and design system adoption. Limitation: "Addons in composed Storybooks will not work as they normally do" — [Storybook docs: Composition (10.6)](https://storybook.js.org/docs/sharing/storybook-composition)
- **[SPLIT]** Visual baselines: Chromatic UI Review shows the exact visual changeset of a branch to designer reviewers — [Chromatic docs: Review](https://www.chromatic.com/docs/storybook/review/)
- **[SPLIT]** The Storybook MCP `test-run` runs component tests and accessibility checks — [Storybook MCP](https://storybook.js.org/docs/ai/mcp/overview)
- **[governance: the design zone vs the dev zone]** Designers change copy, visual values, icons, responsive behaviour and the "what/why" docs. Developers own architecture and logic. Joint calls are made together, and every merge has a human review — [Designed by Thanh (Oct 2026)](https://designedbythanh.substack.com/p/designers-in-the-repo-who-owns-what)

### Inferences
- **Label the code as a proposal.** Each govocal-ds component page could carry a fixed notice. The spec above it (anatomy, states, behaviour, content, tokens, a11y outcomes) is design's commitment. The live component is a *reference implementation* that developers may replace (library, styling, packaging). If an implementation differs from the spec, it gets logged as either a spec change (DECISIONS.md) or an implementation bug. This keeps the reference repo's "spec authoritative" rule for look, behaviour and content, while leaving technology to developers as the brief requires.
- **Write the spec as outcomes.** Keyboard and focus as in APG, roles and states as ARIA terms, sizes and colours as token names, copy as exact strings, anatomy part names as in Open UI and component.gallery. None of these mention React Aria, CSS-in-JS or Tailwind, so they stay true after a migration.
- **Make the stories outlive the code.** If govocal-ds's play functions query by role and label (not `data-testid` or class names), and its visual baselines are pictures, then a developer's reimplementation in another library can be checked against the *same* stories. Developers can ignore the design team's components and still use the design team's tests as their acceptance criteria, which is the most persuasive offer a proposal can make. The catch: stories are written for one renderer (React CSF), so this works directly only while developers stay on React.
- **Composition is the path if developers fork the stack.** If developers build their own library with their own Storybook, the design-owned Storybook can compose theirs through `refs` and keep the spec pages, while the implementation stories come from the developers' Storybook. Addon limits in composed Storybooks (no designs panel or a11y addon on composed stories) mean the design-side checks would then run in the developers' Storybook, which they own.
- **Tokens in DTCG JSON are the hand-off that survives any styling choice.** CSS variables, Tailwind config and CSS-in-JS themes can all be generated from the same file, so design owns the names and values and developers own the pipeline. NL DS runs dozens of municipal themes this way.

### Gaps
- I found no public write-up of a design team that kept a design-owned Storybook while developers replaced the component library underneath. The pattern above is assembled from NL DS, Spectrum, Primer and Storybook's documented features, not from a case study.
- I did not verify how Spectrum's component pages list implementations, nor whether NL DS publishes a single Storybook that composes several framework implementations (it was described only at architecture level).
- Whether CSF stories can be shared across renderers (e.g. React to web components) without rewriting was not researched.

### Inferences
- The DESIGN-OWNED criteria (A1–A7, A9–A13, B1–B4, C1, C2, C4, C5, C7–C11, D5, D7, D9) form the proposal's own scorecard, and all stay valid if developers drop React Aria or change styling technology. Many of them (C2, C4, C5, C8–C10, D9, plus the presence checks in A) can be scripted, which is the evidence developers can rerun themselves.
- The DEV-OWNED criteria (A8, C3, C6 usage, D1, D6, D10) should be reported to developers as observations about the current reference implementation, not as defects, so the audit matches the brief that developers make the strategic implementation calls.

### Gaps
- No published industry benchmark gives pass rates on these specific criteria, so govocal-ds's first audit will set its own baseline. Industry comparison is possible only at the coarse level of zeroheight's inclusion and satisfaction percentages.
