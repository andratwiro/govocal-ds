# Civic / public-sector and React Aria–based Storybook exemplars: a ranked benchmark for the govocal-ds audit

Method note (applies to every section). Each Storybook was checked live on 29 Oct 2026. I fetched its `index.json` (the full sidebar tree: entry count, docs pages vs stories, tags) and its `project.json` (the Storybook version, build date from `generatedAt`, framework and addons). Toolbars (theme, brand, locale, RTL) come from each repo's `.storybook/preview.*`, read through the GitHub API. Repo activity and stars come from the GitHub API, and package versions and weekly downloads from registry.npmjs.org and api.npmjs.org. Wherever a finding says "index.json" or "project.json", the URL is that Storybook's root plus `index.json` or `project.json`.

Ownership tags:
- **[DESIGN-OWNED]**: the practice doesn't depend on the implementation. It stays useful whatever component library, styling technology or packaging the developers choose (token definitions, naming, states, behaviour specs, content rules, acceptance criteria, Figma hygiene, docs).
- **[DEV-OWNED]**: the practice is an implementation decision.
- **[DESIGN-OWNED spec + DEV-OWNED mechanism]**: the "what" is a design artefact and the "how" is code.

---

## Q0 (objective). Ranked catalogue: the exemplar Storybooks, verified live, with "steal this" and weaknesses

### Takeaway
The strongest benchmark is a pairing.
- **NL Design System** and **Designsystemet** show multi-organisation theming and a separation between shared spec and code. That is what a city-branded front office needs.
- **Amsterdam** and **B.C. Gov** show Storybook 10.6-era practice: MCP addon, accessibility tests that fail CI, page templates and a changelog inside Storybook. B.C. Gov is also the only public-sector system built on React Aria Components.
- **Kaizen**, **Hopper** and **React Spectrum S2** are the React Aria references for RTL/locale and multi-brand work.

No public-sector Storybook I found shows every story in an RTL script. Kaizen (79 RTL sticker sheets) and S2 (a 35-locale switcher including ar-AE and he-IL) are the only close matches.

#### Top 8 in depth

**1. NL Design System: the multi-organisation model (themes Storybook + component specs on nldesignsystem.nl)**
- *Live and production*: the themes Storybook (SB 9.1.21, built 2026-10-29) renders 48 organisation themes, mostly municipalities: Utrecht, Rotterdam, Den Haag, Groningen, Haarlem, Leiden, Nijmegen, Tilburg, Zwolle, Zaanstad, Purmerend and others, plus "Start Thema" and "Voorbeeld Thema". Each has Design Tokens docs and a CHANGELOG. — [themes index.json](https://nl-design-system.github.io/themes/index.json), [themes repo: "Design Tokens and NL Design System themes for organisations that don't have their own Storybook"](https://github.com/nl-design-system/themes)
- *Steal this: one component, many cities.* The same Button renders under different organisation themes as sibling stories, e.g. [Utrecht button in Utrecht theme](https://nl-design-system.github.io/themes/?path=/story/utrecht-button--utrecht-theme) vs [the same component in the Voorbeeld (example) theme](https://nl-design-system.github.io/themes/?path=/story/utrecht-button--voorbeeld-theme), and [the candidate button in the Start theme](https://nl-design-system.github.io/themes/?path=/story/nl-button--start-theme). There are whole-organisation sheets such as [Rotterdam :: Components](https://nl-design-system.github.io/themes/?path=/story/rotterdam--components). **[DESIGN-OWNED spec: token sets per organisation + DEV-OWNED mechanism: theme CSS class/stylesheet]**
- *Steal this: the component spec page lives outside any implementation.* https://nldesignsystem.nl/button carries a status badge ("Candidate"), links to Figma, Storybook and npm, and two accessibility checklists: "Acceptatiecriteria bij gebruik" (criteria for whoever uses it) and "Acceptatiecriteria van de component" (criteria for the component). Each criterion cites a WCAG SC and level and is tagged by role (designer / developer / contentmaker). The page then lists the implementations (Amsterdam, Utrecht, Den Haag) with their own Figma, GitHub, Storybook and npm links. — [NLDS Button](https://nldesignsystem.nl/button) **[DESIGN-OWNED]**
- *Steal this: a maturity model with explicit exit criteria* (Help Wanted → Community → Candidate → Hall of Fame). — [Estafettemodel](https://nldesignsystem.nl/handboek/estafettemodel/), [Definition of Done](https://nldesignsystem.nl/componenten/definition-of-done) **[DESIGN-OWNED governance]**
- *Weak*: it is split across many Storybooks and sites (themes, Den Haag, Amsterdam, a Utrecht URL that 404'd, a candidate URL showing "Site not found"). The spec lives on the website rather than in Storybook. Most content is Dutch-only. The themes Storybook is on SB 9.1, a major behind Amsterdam and Den Haag (10.6). — [themes project.json](https://nl-design-system.github.io/themes/project.json), [candidate homepage](https://nl-design-system.github.io/candidate/)

**2. Designsystemet (Norway, Digdir): theme builder + CSS-first + accessibility tests on every story**
- *Live and production*: SB 10.6.0 (built 2026-09-25); `@digdir/designsystemet-react` and `-css` 1.23.0 (2026-09-25), about 18.6k / 19.3k downloads a week; "over 300 organisations and over 1,400 people" in the community. — [project.json](https://storybook.designsystemet.no/project.json), [npm react](https://www.npmjs.com/package/@digdir/designsystemet-react), [About Designsystemet](https://designsystemet.no/en/fundamentals/introduction/about-the-design-system/)
- *Steal this: the principle that answers "will every city look the same?"* "The goal of Designsystemet is not that all services should look exactly the same, but that components should behave the same—for example, in screen readers and assistive technologies." — [About Designsystemet](https://designsystemet.no/en/fundamentals/introduction/about-the-design-system/) **[DESIGN-OWNED]**
- *Steal this: the Theme Builder* (https://theme.designsystemet.no). It saves a `designsystemet.config.json`, and the CLI generates design tokens, CSS and (through Tokens Studio) Figma variables. It supports light/dark/contrast modes and multiple themes side by side. — [Build your theme](https://designsystemet.no/en/fundamentals/themebuilder/own-theme/) **[DESIGN-OWNED inputs + DEV-OWNED CLI]**
- *Steal this: an accessibility tab per component, written as "What you need to check".* Each item is tied to a WCAG 2.2 SC, e.g. "The accessible name must match the visible text… WCAG 2.5.3 Label in Name". It is published in English and Norwegian (`components/button/{en,no}/{overview,code,accessibility}.mdx`). — [button accessibility.mdx](https://github.com/digdir/designsystemet/blob/main/apps/www/app/content/components/button/en/accessibility.mdx) **[DESIGN-OWNED]**
- *Steal this: tests visible in the sidebar.* All 377/377 entries carry the `a11y-test` tag, and the preview sets `a11y: { test: 'error' }`, so a violation fails CI. There are 81 play functions and a "Chromatic" group of 36 snapshot stories (e.g. [Chromatic/Button :: Snapshots](https://storybook.designsystemet.no/?path=/story/chromatic-button--snapshots)), plus a "Story Theme" toolbar (Light/Dark/Auto). — [index.json](https://storybook.designsystemet.no/index.json), [preview.tsx](https://github.com/digdir/designsystemet/blob/main/apps/storybook/.storybook/preview.tsx) **[DEV-OWNED]**
- *Weak*: the Storybook sidebar is in Norwegian ("Komponenter", "Avviklet" = deprecated), and Storybook holds only 47 docs pages: guidance lives on designsystemet.no, so Storybook is a dev workbench. No RTL stories (one keyword hit, a dark typography example). — [index.json](https://storybook.designsystemet.no/index.json)

A `DesignTokensTable` is fed from `button.tokens.json`. — [Button docs](https://amsterdam.github.io/design-system/?path=/docs/components-buttons-button--docs), [Button.docs.mdx](https://github.com/Amsterdam/design-system/blob/main/storybook/src/components/Button/Button.docs.mdx) **[DESIGN-OWNED]**
- *Steal this: a public MCP endpoint and an "AI assistance" page.* It exposes `list-all-documentation`, `get-documentation` and `get-documentation-for-story` at `https://main--68db9df886b46f139748c074.chromatic.com/mcp`, tracking `main`. — [AI assistance](https://amsterdam.github.io/design-system/?path=/docs/docs-guidelines-ai-assistance--docs), [source](https://github.com/Amsterdam/design-system/blob/main/storybook/src/docs/guidelines/ai-assistance.docs.mdx) **[DEV-OWNED infrastructure; serves DESIGN-OWNED content]**
- *Steal this: a definition of done anyone can audit.* It covers manual screen-reader checks (NVDA+Chrome, VoiceOver+Safari), 200% zoom, maximum text size, WCAG 1.4.12 text spacing, forced colours, RTL, no-CSS and no-JS degradation, and token hygiene ("All tokens used are defined. No unused tokens are defined."). — [definition-of-done.md](https://github.com/Amsterdam/design-system/blob/main/documentation/definition-of-done.md) **[DESIGN-OWNED criteria + DEV-OWNED checks]**
- *Weak*: one brand only (no theme switcher); RTL is a manual "additional" check, with no RTL stories (only "Translated" stories, e.g. [Form Field Status :: Translated](https://amsterdam.github.io/design-system/?path=/story/components-forms-form-field-status--translated)); usage examples are Dutch-centric (e.g. "Use the verb's infinitive form in Dutch").

## Q2. Multi-tenant / multi-brand theming through tokens, and how Storybook shows it

### Takeaway
Three working models.
1. **Token-set-per-organisation over white-label components**: NL Design System (48 themes in one Storybook, sibling stories per theme) and Designsystemet (a Theme Builder writes a config file, then the CLI emits tokens, CSS and Figma variables).
2. **A brand toolbar over a fixed set of brand stylesheets**: CMS (core/Healthcare/Medicare), SGDS (GovTech palettes), AgDS (Agriculture/DAFF), Hopper (Workleap/ShareGate).
3. **Theme props on components**: Helsinki HDS.

For many cities, model 1 is the one that scales. Model 2 is the cheap way to *show* it in Storybook.

## Q3. Accessibility documentation: WCAG 2.2 / EN 301 549 statements, keyboard tables, screen-reader notes, test evidence

### Takeaway
The best civic practice splits accessibility into **what the component guarantees** and **what the consumer must still check**, each criterion tied to a WCAG 2.2 SC. NLDS does this, adding role tags; Designsystemet does it as "What you need to check". The proof that convinces developers is accessibility tests that fail CI (Designsystemet, B.C. Gov, SGDS: `a11y.test: 'error'`), plus a public definition of done that lists manual screen-reader and zoom checks (Amsterdam). No checked system gave per-component EN 301 549 statements.

### Cited Findings
- NLDS component pages list "Acceptatiecriteria bij gebruik" (consumer criteria) and "Acceptatiecriteria van de component" (component criteria), each with a WCAG SC number and level and tagged by role (designer, developer, contentmaker). — [NLDS Button](https://nldesignsystem.nl/button) **[DESIGN-OWNED]**
- NLDS Candidate stage requires "Semantiek (roles, names, states in HTML/ARIA) is goedgekeurd" (semantics approved); Hall of Fame requires security/privacy docs and production proof at two or more organisations. — [Definition of Done](https://nldesignsystem.nl/componenten/definition-of-done)
- Designsystemet's per-component accessibility page, "What you need to check": e.g. "Button text must clearly describe the action… WCAG: 2.4.4"; "The accessible name must match the visible text… WCAG: 2.5.3 Label in Name"; icons in text buttons decorative (1.1.1). — [accessibility.mdx](https://github.com/digdir/designsystemet/blob/main/apps/www/app/content/components/button/en/accessibility.mdx) **[DESIGN-OWNED]**
- Amsterdam: "We build and test every component against WCAG 2.2 Level AA". It explains the legal baseline (the Wet Digitale Overheid requires WCAG 2.1 AA, and 2.2 is backwards compatible); "Accessibility tests run in Chromatic on every component with a Test story, with each pull request"; manual checks live in the definition of done. — [Accessibility guideline](https://amsterdam.github.io/design-system/?path=/docs/docs-guidelines-accessibility--docs), [source](https://github.com/Amsterdam/design-system/blob/main/storybook/src/docs/guidelines/accessibility.docs.mdx)

- CI gates: Designsystemet `tags: ['a11y-test']` on all stories and `a11y: { test: 'error' }` ([preview.tsx](https://github.com/digdir/designsystemet/blob/main/apps/storybook/.storybook/preview.tsx)); B.C. - Italia tags 589 component stories `a11y-ok` and has a top-level "Accessibilità" page. — [Italia index.json](https://italia.github.io/dev-kit-italia/index.json), [Accessibilità](https://italia.github.io/dev-kit-italia/?path=/docs/accessibilità--documentazione)
- HDS has an accessibility tab per component ("Pay attention to" + "Related accessibility requirements"); it cites WCAG 2.1 SCs, and the Button page notes the buttons meet 2.5.5 Target Size (AAA). — [HDS accessibility.mdx](https://github.com/City-of-Helsinki/helsinki-design-system/blob/development/site/src/docs/components/button/accessibility.mdx)
- Kaizen applies global axe rules (`globalA11yRules`), and usage docs carry accessibility-focused writing rules ("Button labels should make sense in isolation… distinct, accessible names"). — [Kaizen preview.tsx](https://github.com/cultureamp/kaizen-design-system/blob/main/docs/.storybook/preview.tsx), [usage guidelines](https://github.com/cultureamp/kaizen-design-system/blob/main/packages/components/src/Button/_docs/Button--usage-guidelines.mdx)
- GOV.UK weaves accessibility into the guidance (warning buttons mustn't rely on colour alone; inverse buttons need 4.5:1; disabled buttons "have poor contrast and can confuse some users, so avoid them if possible"). — [GOV.UK Button](https://design-system.service.gov.uk/components/button/)

### Inferences
- The most teachable pattern for a designer is the NLDS/Designsystemet consumer checklist: it tells the person composing a page what they still own. It is **DESIGN-OWNED** and needs no code. The most convincing evidence for a developer is a CI gate plus a definition of done they can read. A tagged sidebar (Designsystemet's `a11y-test` on 377/377) makes the coverage visible without opening CI.
- Citing WCAG 2.2 rather than 2.1 is now standard among current civic peers (Amsterdam, Designsystemet). HDS still links 2.1.

### Gaps
- None of the checked Storybooks had a **keyboard interaction table** as a standard docs block. Keyboard behaviour is usually left to React Aria's docs (B.C. Gov, Kaizen) or written as prose. I found no EN 301 549 clause mapping per component in any of them.
- I found no published per-component screen-reader test logs (date, AT, browser, result). Amsterdam's definition of done names the AT pairs but publishes no results per component.

### Takeaway

## Q5. React Aria–based systems: behaviour (from React Aria) vs styling (their own), exposing props without leaking complexity, and what survives another headless library

### Takeaway
The best React Aria systems **name the dependency and link out for behaviour** (B.C. Gov's "This is a React Aria component" banner). They **curate a small core API and push the rest into an "additional options" table** (Kaizen). Behaviour then isn't re-documented, but the team still owns usage, anatomy, tokens and writing rules. If developers dropped React Aria, nearly all of that **DESIGN-OWNED** layer would survive; what would be lost is the API docs, render props, `onPress` semantics and `I18nProvider` locale wiring.

### Cited Findings
- B.C. Gov docs pages open with an InlineAlert, "This is a React Aria component… based on the RA Button component. Consult the React Aria docs to understand its full API", linking https://react-aria.adobe.com/Button. Usage guidance and Figma are linked separately on gov.bc.ca. — [B.C. Button.mdx](https://github.com/bcgov/design-system/blob/main/packages/react-components/src/stories/Button.mdx), [live](https://designsystem.gov.bc.ca/react-components/?path=/docs/inputs-and-controls-button--docs)
- B.C. Gov keeps link styling apart from button behaviour: "To create a hyperlink that looks like a button, use a Link component with the `isButton` and `buttonVariant` props." — [B.C. Button.mdx](https://github.com/bcgov/design-system/blob/main/packages/react-components/src/stories/Button.mdx)
- Kaizen's API spec: "This is built on top of React Aria's Button component and seeks to provide a flexible API with convenient abstractions that handles variants, sizes, pending states and icons". It explains the `onClick` → `onPress` shift ("better support for consistent touch events across device types"), lets `children` take React Aria's `ButtonRenderProps`, and has an "Additional API options" table: "a collection of additional React Aria and native HTML props… not required… but can be used to extend its functionality". — [Kaizen Button API Specification](https://github.com/cultureamp/kaizen-design-system/blob/main/packages/components/src/Button/_docs/Button--api-specification.mdx), [live](https://cultureamp.design/?path=/docs/components-button-api-specification--docs)
- Kaizen's Usage Guidelines page holds no React Aria content: Overview, Anatomy, When to use / When not to use, Specs, Dos and don'ts, writing rules. — [Kaizen usage guidelines](https://github.com/cultureamp/kaizen-design-system/blob/main/packages/components/src/Button/_docs/Button--usage-guidelines.mdx)

- The RAC starters are deliberately bare (one autodocs page plus stories per component, no usage guidance), meant as a base for "a full component library". — [getting started](https://react-aria.adobe.com/getting-started), [Vanilla starter index.json](https://react-aria.adobe.com/react-aria-starter/index.json)
- HeroUI v3 is "built on React Aria Components for accessibility and Tailwind CSS v4 for styling" and tracks React Aria releases (v3.2.7 bumps react-aria-components to 1.22.1). — [HeroUI v3.2.7](https://heroui.com/en/docs/react/releases/v3-2-7), [InfoQ](https://www.infoq.com/news/2026/07/heroui-v3-rewrite/)
- Hopper wraps React Aria Components in a styled-system package (`@hopper-ui/styled-system`) with brand theme CSS; behaviour comes from React Aria, while look and brand belong to Hopper. — [Hopper preview.tsx](https://github.com/workleap/wl-hopper/blob/main/.storybook/preview.tsx), [wl-hopper repo](https://github.com/workleap/wl-hopper)

What would survive a switch to another headless library:

| System | Survives (implementation-agnostic) | Lost (tied to React Aria) |
|---|---|---|
| B.C. Gov | tokens/CSS, Figma library, usage guidance on gov.bc.ca, Template stories as visual specs, changelog discipline, CI a11y gate | the "This is a React Aria component" framing, RA prop API, Code Connect mappings to RA props |
| Kaizen | Usage Guidelines (anatomy, do/don't, writing rules), RTL and locale sticker sheets as a test matrix, global axe rules | API Specification (onPress, ButtonRenderProps, the additional RA props table), the `I18nProvider` decorator |
| Hopper | per-brand semantic token sets (light/dark), brand stylesheets, toolbar *concept* | component internals, any RA-specific props |
| RAC starters / S2 | the locale test list (35 locales incl. ar-AE/he-IL), S2 as a visual reference | everything else (they *are* React Aria) |

(Sources: the rows above restate the cited findings in this section and Q0. The table is my classification.)

### Inferences
- For govocal-ds, which is a design-side proposal whose developers may drop React Aria, the Kaizen split is the safe pattern. Keep a **Usage** page (DESIGN-OWNED, survives any library) separate from an **API** page (DEV-OWNED, swappable). The RTL/LTR matrix and the states/behaviour specs can then outlive the React Aria choice.
- Keyboard behaviour specs written against WAI-ARIA APG patterns (https://www.w3.org/WAI/ARIA/apg/patterns/), rather than "see React Aria docs", would survive a library change. B.C. Gov's link-out is efficient but ties the behaviour docs to React Aria. This is my judgement, not something a source states.

### Gaps
- I didn't verify how Hopper's docs site (hopper.workleap.design) splits behaviour from styling per component. Only its Storybook config and token stories were read.
- I found no public post-mortem of a team migrating *off* React Aria to another headless library (Radix, Ariakit, Base UI) that names what docs survived.

## Q8. How do shared-spec systems separate the shared spec from the code, and which practices are design-owned vs dev-owned?

### Takeaway
NL Design System and Designsystemet both treat the **specification** (component definition, acceptance criteria, token conventions, themes) as a shared public good, separate from any one **implementation**.
- **NLDS** does it organisationally. A spec page per component lists several organisations' implementations. A relay model promotes a component only when two or more organisations with *different house styles* use it, with no organisation-specific API and `nl`-prefixed tokens. Packages are split into tokens / CSS / React / docs.
- **Designsystemet** does it technically. CSS is the framework-independent core, React is one binding, a CLI and Theme Builder own the tokens, and bilingual docs tabs split overview / code / accessibility.

## Q9 (project-lead lens). Who owns the component code, and how are consumers kept inside the system's visual language?

Context for this lens: the design side will own the Storybook component code (built with AI agents), and developers will import it to compose screens, so design controls the visual language. The question is how exemplars (1) assign ownership of component code and (2) stop consumers drifting out of the language: restricted styling APIs, escape hatches, token-only layout props, and theming without overriding components.

### Takeaway
In every exemplar, a **central team owns the component code and product teams import it**, the same shape as the govocal-ds plan. NL Design System is the exception: the core team owns only the shared candidate, and each municipality owns its own implementation and theme. The strongest guardrails are in the React Aria systems.
- **React Spectrum S2**: a `styles` prop that accepts only layout, spacing, size and position, built through a token-only `style` macro; colours and internal padding are off-limits; `UNSAFE_className` / `UNSAFE_style` are a typed "last resort".
- **Hopper**: style props accept tokens only by default, with a short whitelist of `UNSAFE_`-prefixed props.

The civic systems use softer, token-level guardrails.
- **NLDS**: component CSS reads only `--nl-<component>-*` tokens, themes are JSON token files, and organisation-specific APIs are forbidden at Candidate stage.
- **Designsystemet**: colour is chosen only through `data-color` / `data-color-scheme` attributes that mirror Figma's "Appearance" properties.
- **Amsterdam**: layout props are typed to token names.

Most still accept a plain `className` (merged by Designsystemet and Kaizen; *replacing* the component's classes in B.C. Gov's Button).

#### (2) How consumers are kept inside the language

- **React Spectrum S2: the strictest model (React Aria).**
  - The `style` macro applies Spectrum 2 design tokens only.
  - "The `styles` prop accepts a limited set of CSS properties, including layout, spacing, sizing, and positioning. Other styles such as colors and internal padding cannot be customized within Spectrum components."
  - In source, `allowedOverrides` starts with margin, marginStart, marginEnd…, and the type is `StylesProp = StyleString<allowedOverrides | widthProperties>`.
  - The escape hatches are typed `UNSAFE_className?: UnsafeClassName` (a `string & {properties?: never}`) and `UNSAFE_style`, each documented "Only use as a **last resort**. Use the `style` macro via the `styles` prop instead."
  - Sources: [S2 Styling](https://react-spectrum.adobe.com/styling), [style-utils.ts](https://github.com/adobe/react-spectrum/blob/main/packages/@react-spectrum/s2/src/style-utils.ts). **[DESIGN-OWNED rule (what consumers may change) + DEV-OWNED mechanism (macro/types)]**
- **Hopper: tokens by default, named escape hatch (React Aria).** "In general, customizing Hopper is discouraged, but most components do offer control over layout… By default, only tokens are accepted as values for style props… If you need to pass a custom value, you can use the `UNSAFE_` prefix to bypass the token system." Only a whitelist of props has `UNSAFE_` versions (e.g. `UNSAFE_fontSize="1.5rem"` allowed; `top` takes no token). The `UNSAFE_*Value` types are declared in `styledSystemProps.ts`. — [Hopper styling concept](https://github.com/workleap/wl-hopper/blob/main/apps/docs/content/styled-system/concepts/styling.mdx), [styledSystemProps.ts](https://github.com/workleap/wl-hopper/blob/main/packages/styled-system/src/styledSystemProps.ts), [styled-system concept](https://github.com/workleap/wl-hopper/blob/main/apps/docs/content/components/concepts/styled-system.mdx) **[DESIGN-OWNED token whitelist + DEV-OWNED types]**
- **Kaizen: additive className (React Aria).** Button wraps React Aria's `RACButton`, styles with CSS Modules, and merges a consumer `className` with its own (`mergeClassNames(styles.button, styles[size], …)`). There is no `UNSAFE_` naming, so the escape hatch is open but doesn't replace base styles. — [Kaizen Button.tsx](https://github.com/cultureamp/kaizen-design-system/blob/main/packages/components/src/Button/Button.tsx) **[DEV-OWNED]**
- **B.C. Gov: open passthrough (React Aria).** `ButtonProps extends ReactAriaButtonProps`. The component sets `className={\`bcds-react-aria-Button ${size} ${variant} …\`}` and then spreads `{...props}` *after* it. — [B.C. Button.tsx](https://github.com/bcgov/design-system/blob/main/packages/react-components/src/components/Button/Button.tsx) **[DEV-OWNED]**
- **Designsystemet: colour only through theme attributes that mirror Figma.**
  - "HTML data attributes are used to define the color of a component. The components can use all colors in the theme."
  - `data-color-scheme` "corresponds with `Appearance › Color scheme` in Figma", and `data-color` "corresponds with `Appearance › Color` in Figma".
  - Button `variant` is a closed union (`'primary' | 'secondary' | 'tertiary'`), and a consumer `className` is merged (`cl('ds-button', className)`).
  - Sources: [Colors in code](https://github.com/digdir/designsystemet/blob/main/apps/www/app/content/fundamentals/en/code/colors.mdx), [button.tsx](https://github.com/digdir/designsystemet/blob/main/packages/react/src/components/button/button.tsx). **[DESIGN-OWNED (theme colour names = Figma properties) + DEV-OWNED (attributes)]**
- **NL Design System: theme by token values, never by overriding components.** The candidate Button's CSS reads only component tokens (`var(--nl-button-border-radius`, `--nl-button-default-background-color`, `--nl-button-default-active-border-color`, …). "Themes are JSON files that contain and define design tokens". Candidate stage forbids organisation-specific APIs ("Geen organisatie specifieke API's meer") and requires `nl`-prefixed tokens. — [candidate button `_mixin.scss`](https://github.com/nl-design-system/candidate/blob/main/packages/components-css/button-css/src/_mixin.scss), [themes README](https://github.com/nl-design-system/themes), [Definition of Done](https://nldesignsystem.nl/componenten/definition-of-done) **[DESIGN-OWNED (component token contract) + DEV-OWNED (CSS)]**
- **Amsterdam: token-only layout props enforced by types.** `Grid` accepts `gap` from `['none', 'large', '2x-large']` and padding from `['large', 'x-large', '2x-large']`. `paddingVertical` and `paddingTop`/`paddingBottom` are mutually exclusive through `never` types, and column and row counts are typed unions (`GridColumnNumber = 1 … 12`). — [Amsterdam Grid.tsx](https://github.com/Amsterdam/design-system/blob/main/packages/react/src/Grid/Grid.tsx) **[DESIGN-OWNED spacing scale + DEV-OWNED types]**
- **Amsterdam: token hygiene enforced at review.** "All tokens used are defined. No unused tokens are defined." — [definition-of-done.md](https://github.com/Amsterdam/design-system/blob/main/documentation/definition-of-done.md)
- **CMS and SGDS: brand switching without touching components.** CMS swaps a whole `${theme}-theme.css` and sets `data-theme`; SGDS adds a brand class on `<html>`. In both, components read the switched variables. — [CMS preview.tsx](https://github.com/CMSgov/design-system/blob/main/.storybook/preview.tsx), [SGDS preview.ts](https://github.com/GovTechSG/sgds-web-component/blob/master/.storybook/preview.ts) **[DEV-OWNED mechanism over DESIGN-OWNED token sets]**
- **HDS: the counter-example.** Theming goes through component theme props ("Custom theme" stories on 20 components), and the docs warn that customised colours must be checked against the colour guidelines. — [Hero :: Playground For Theme](https://hds.hel.fi/storybook/react/?path=/story/components-hero--playground-for-theme), [HDS accessibility.mdx](https://github.com/City-of-Helsinki/helsinki-design-system/blob/development/site/src/docs/components/button/accessibility.mdx)

### Inferences
- In B.C. Gov's Button, a consumer `className` would *replace* `bcds-react-aria-Button …` because the spread comes last, dropping the system's styling. That is the opposite of a guardrail. Kaizen and Designsystemet merge instead. This is my reading of the JSX order, not a documented B.C. Gov behaviour.
- For a design-owned component library that developers import, the S2 / Hopper pattern is the most direct way to keep the language intact: layout-only overrides, token-only values, and escape hatches named `UNSAFE_`. The *whitelist* of what a consumer may change (layout/spacing/size yes; colour and internal padding no) is a **DESIGN-OWNED** decision that survives any library change. The macro or type that enforces it is **DEV-OWNED**. Developers who take over the stack can keep the whitelist even if React Aria goes.
- For city branding, the civic pattern that avoids component overrides is NLDS's component-token contract (`--nl-button-*` filled from a theme JSON) combined with Designsystemet's rule that colour enters only through named theme roles mirrored in Figma. A city then changes token values, never component code or props. HDS's theme props show what happens otherwise: brand leaks into the component API and the contrast burden moves to the consumer.
- No exemplar documents how an AI agent is prevented from adding non-token values. Amsterdam's token-hygiene rule plus S2-style typed `styles` props would be the nearest guard, enforced by types and lint rather than by docs.
