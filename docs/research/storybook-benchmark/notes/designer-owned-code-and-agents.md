# Design teams owning component-library CODE, built with AI agents, composed by developers (2025–2026)

Scope note for the report writer: sources are 2025–2026 unless marked **(background/origin)**. Vendor posts (Builder.io, Chromatic, Figma, Vercel, Anthropic) are marked **(vendor)**; treat their claims as the vendor's own. No individual at Go Vocal is named. Sibling notes in this folder already cover tokens (`tokens.md`), docs/language (`designer_bible_and_language.md`), developer trust/semver/QA (`developer_trust_and_ai.md`) and audit rubrics (`audit_rubrics.md`); this file covers designer ownership of component code with agents, the composition boundary, the agent interface, code-first Figma sync, the developer contract, and review of component changes in Storybook, and ends with a practice list. **Out of scope (project lead's instruction):** how any separate prototype tool consumes the library (bundles, CDN builds, import maps, web-component wrappers) and the prototype → product path. This file does not cover them.

## 1. Ownership models: who owns production component code, who composes, how reviews split

### Takeaway
Some teams do let designers or design engineers own production UI code, but the 2025–2026 public cases almost all keep an engineer approval in the loop. The split shows up in repo mechanics: CODEOWNERS default to engineer reviewers, design reviewers own the theme/token paths, and a required visual review check sits next to code review. A model where designers own the library, say through Storybook, and developers only compose from it is not documented as a named, public practice at a large company. The closest analogues are design-engineering teams (Vercel, GitHub's Design Infrastructure) and "designers ship to prod with an engineer approving" (Intercom).

### Cited Findings
- **Vercel (background/origin, Mar 2024):** Vercel's design engineers maintain the internal design-system components used across Vercel.com, the Vercel Toolbar and the Next.js docs. They "design, build, and ship a solution autonomously". When a designer helps on a feature, "the Design Engineer implements the UI while the product team implements the API and infrastructure." — [Vercel: Design Engineering at Vercel](https://vercel.com/blog/design-engineering-at-vercel)
- **GitHub Primer (background):** Primer is maintained by GitHub's Design Infrastructure and Design Engineering teams. Primer's own pages say GitHub product and web designers contribute production code and that "every product and web designer" writes CSS. — [Primer: Meet the team](https://primer.github.io/design/about/) (search-snippet level; older page)
- **Primer's review split in the repo itself:** `primer/react`'s CODEOWNERS assigns `* @primer/engineer-reviewers` (comment: "All changes should be reviewed by a member of the @react-reviewers team") and assigns `./packages/react/src/legacy-theme/` to `@primer/design-reviewers`. So engineers gate every change and designers own the theme path. — [primer/react CODEOWNERS](https://github.com/primer/react/blob/main/CODEOWNERS) (read from `main`, 29 Oct 2026)
- **Shopify Polaris:** CODEOWNERS gives `/polaris-tokens` and `/polaris-icons` to named maintainers, i.e. path-level ownership of the visual foundations. — [Shopify/polaris .github/CODEOWNERS](https://github.com/Shopify/polaris/blob/main/.github/CODEOWNERS)
- **Mechanism:** CODEOWNERS plus branch protection "require review from Code Owners" lets different teams own different paths. — [GitLab docs: Code Owners](https://docs.gitlab.com/user/project/codeowners/); the pattern of design and engineering both approving is described in [Bump.sh: API design reviews](https://bump.sh/blog/api-design-reviews/)
- **Intercom (2026):** "100% of engineers—plus designers, PMs, and TPMs—now shipping code via Claude Code". Merged PRs per R&D employee doubled in nine months. Quality is enforced by "a skills repository with hooks that enforce engineering standards automatically" and a custom "Create PR" skill. — [Lenny's Newsletter / How I AI, 20 Apr 2026](https://www.lennysnewsletter.com/p/how-intercom-2xd-their-engineering). The search summary of the same page says the Create PR skill "blocks Claude Code from using the GitHub CLI directly and forces it to write context-rich PR descriptions" — [same source](https://www.lennysnewsletter.com/p/how-intercom-2xd-their-engineering)
- **Intercom (background/origin, 2017):** the designer-ships-code rule set predates AI. A change qualifies if it is design-focused (not JavaScript logic), small, quick, and something the designer is confident in. An engineer approves the PR. — [Intercom: Shipping code for designers, not just engineers](https://www.intercom.com/blog/shipping-code-designers/)
- **Survey (AI in Design Report 2026, published 6 Oct 2026, fielded Q1 2026):** 50% of respondents have shipped AI-generated code to production, and 76% have used AI coding tools (Claude Code, Cursor, Codex, Copilot). The share is 68% at early-stage companies versus 33% at public companies. 43% now expect working prototypes as a standard design deliverable. The sample size is not shown on the chapter page. — [stateofaidesign.com: Craft](https://stateofaidesign.com/chapters/craft). The site's summary of the same report says only 20% of those who shipped code call themselves design engineers — [stateofaidesign.com](https://stateofaidesign.com/)
- **Atlassian:** about 1,000 product designers and PMs were trained to prototype with AI on the Atlassian Design System (ADS). The ADS team supplies the context (MCP, guidelines, templates). — [Atlassian: Turning handoffs into handshakes, 26 Nov 2025](https://www.atlassian.com/blog/how-we-build/turning-handoffs-into-handshakes-integrating-design-systems-for-ai-prototyping-at-scale)

### Inferences
- The defensible public pattern is "design owns the visual language and its files; engineering owns the public API and approves merges". The repo encodes it: CODEOWNERS paths, a required visual-review check, and a required code-owner review. No source shows designers owning a library with no engineering gate.
- For a two-designer team that owns the Storybook, the developer-facing contract has to be explicit. Developers keep approval over exported API surface (prop names and types, exports, package boundaries). Designers own tokens, CSS, stories and docs. This matches how Primer splits ownership.

### Gaps
- No 2025–2026 primary write-up was found from Linear, Figma or Shopify describing a designer-owned production component library composed by product engineers. Their public material is about craft or AI prototyping, not repo ownership.
- No rigorous 2025–2026 "design engineer" role survey with a disclosed sample was found. The AI in Design Report does not show its n on the pages read.

## 2. Designers building production UI with AI coding agents: case studies, guardrails, failure modes

### Takeaway
Designers now commonly build in code with agents. The guardrails that hold up are structural: preconfigured templates, long system-specific instruction files, MCP context, hook-enforced skills, small PRs, labelled and auditable AI review, and engineer accountability for production. The failure modes are consistent across sources. Agents invent components, props, token names and icons, rewrite code they shouldn't touch, and revert to old APIs, and reviewers get buried under larger PRs.

### Cited Findings
- **Atlassian failure modes (Nov 2025):** "Incorrect component imports, wrong token names, icons that seem on-brand but don't exist, or the wrong size/name applied to the right thing". Prompt-based logo changes made the model "rewrite code that shouldn't change, or revert to older component APIs". Most AI prototyping tools don't support their Compiled CSS-in-JS. "Generating production-quality code at scale remains challenging." — [Atlassian, 26 Nov 2025](https://www.atlassian.com/blog/how-we-build/turning-handoffs-into-handshakes-integrating-design-systems-for-ai-prototyping-at-scale)
- **Atlassian guardrails (Nov 2025):** templates ship preconfigured code with design-system instructions, feature flags, navigation and theme switchers ("cut frustration, curbed hallucinations"). A single ~2,000-line `guidelines.md` puts high-priority guidance at the top. JSON config files for logo and navigation keep the model from rewriting unrelated code. Result: "From a screenshot, AI prototyping reaches about 70% Atlassian Design System accuracy in one pass." — [same source](https://www.atlassian.com/blog/how-we-build/turning-handoffs-into-handshakes-integrating-design-systems-for-ai-prototyping-at-scale)
- **Intercom AI PR approval (21 Apr 2026):** AI may approve only appropriately scoped PRs. It "won't approve large PRs" and flags oversized ones for breakdown. "Every AI-approved PR is labelled, logged, and queryable". The person shipping stays accountable for production. 19% of PRs are auto-approved with no human reviewer. Frontend revert rate is 0.22% for AI-approved versus 2.00% for human-reviewed (backend 0.53% vs 5.39%). — [Intercom blog](https://www.intercom.com/blog/ai-is-approving-our-pull-requests-heres-how-we-made-it-safe)
- **Intercom design workflow (Mar 2026, secondhand summary of a talk):** designers prototype with Figma MCP plus Claude Code plus **Code Connect**, which maps each Figma component to its codebase import path. Without that link, "AI gets visual information but reinvents components from scratch." Prototypes deploy as GitHub PRs. The caveat given is that it took dedicated teams and months of work. — [rogerwong.me summary](https://rogerwong.me/2026/03/figma-mcp-compounding-design-system-domingo-widen) of [the original video](https://www.youtube.com/watch?v=_9OdGDjFrCw)
- **Intercom company-wide Claude Code (23 Mar 2026):** more than 1,000 people have access, 300+ are weekly active, and 330 pages were published in one week. The non-engineers' "guidance skills" are domain knowledge packs. The post does not cover code-review guardrails. — [Fin Ideas](https://ideas.fin.ai/p/we-gave-claude-code-to-everyone-at)
- **Review burden data (Faros, 21 May 2026; telemetry the article attributes to about 22,000 developers on 4,000 teams):** under high AI adoption, PR size rose 51.3%, files per PR 59.7% and bugs per PR 54%. Median time in review rose 441.5%, and PRs merged with no review rose 31.3%. Their recommendation: "Stop trying to out-review bad AI output. Fix what AI sees before it writes." — [Faros AI](https://www.faros.ai/blog/ai-code-quality-senior-engineer-review-burden)
- **Builder.io Fusion (vendor, 3 Sep 2025):** designers edit live components on a branch and Fusion opens a PR. "Nothing you do ships until a developer reviews and approves it." The scope is padding, colour, font size, spacing and reordering. Larger work still starts in Figma. — [Builder.io](https://www.builder.io/blog/designers-can-ship-without-engineering-handoffs)
- **Claude Design (reported 17 Jun 2026):** you import a design system from a GitHub repo, and the tool "checks its output against the design system, and auto-corrects before the user ever sees the result". Admins can lock edits. `/design-sync` pulls the codebase's system in so prototypes use real components, and output hands to Claude Code "with no rebuilding needed". — [VentureBeat](https://venturebeat.com/technology/anthropic-ships-major-claude-design-overhaul-with-design-system-imports-code-round-trips-and-a-fix-for-its-token-burning-problem); launch post (vendor) [Anthropic: Introducing Claude Design](https://www.anthropic.com/news/claude-design-anthropic-labs)
- **Generic vibe-coding drift:** tools that "don't know your component library exists" produce off-scale spacing and mismatched buttons. — [Builder.io: limitations of vibe coding tools (vendor)](https://www.builder.io/m/explainers/vibe-coding-limitations)

### Inferences
- The guardrails that have evidence behind them sit before generation (context, templates, MCP) and at merge (small PRs, labelled AI review, required checks). Faros's data says downstream review alone does not scale.
- For an agent-built library, the strongest proof for a skeptical developer is a CI that would catch the Atlassian failure list. That means failing on unknown imports, unknown token names and unknown icons, and diffing the public API on every PR.

### Gaps
- No public 2025–2026 case study was found of a design-system team that built its whole component library with agents and published defect or quality data on it. The public cases are prototyping, product UI, or system docs/context.
- One widely repeated statistic, that "600 vibe-coded apps with design systems had 67% better UI consistency", traces only to a low-quality blog ([blog.vibecoder.me](https://blog.vibecoder.me/design-systems-vibe-coded-apps-deep-dive)) with no methodology. Treat it as unreliable.

## 3. The composition boundary: letting developers compose while design keeps the language

### Takeaway
The leading systems shrank what consumers can style. Spectrum 2 limits its `styles` prop to layout, spacing, sizing and position, and flags `UNSAFE_` escape hatches. Atlassian's xcss and primitives accept tokens only, with no nested selectors and no `className` on ADS components, enforced by a large ESLint rule set. Polaris web components cannot be overridden by CSS at all. Primer removed `sx`. Panda can make raw values a TypeScript error. Layout primitives with token-scale props, plus slots and compound components, give composition its freedom. Adoption is then measured from rendered DOM or static scans.

### Cited Findings
- **React Spectrum S2:** the `styles` prop accepts only layout, spacing, sizing and positioning properties. "Colors and internal padding cannot be customized within Spectrum components." The `style` macro runs at build time, takes Spectrum 2 token values, and emits atomic CSS. Custom components are built from React Aria Components plus the style macro. — [React Spectrum: Styling](https://react-spectrum.adobe.com/styling). Using `UNSAFE_className` "is strongly discouraged because it results in inconsistent UIs and hard to maintain code". Style macros passed to `UNSAFE_className` "will now result in a TypeScript error" because it is appended, not merged. — [S2 release notes](https://react-spectrum.adobe.com/beta/s2/release-notes.html) (via search excerpt; the page did not render for direct fetch)
- **Atlassian:** xcss "restricts nested selectors completely" and limits most style attributes to token values — [Forge XCSS](https://developer.atlassian.com/platform/forge/ui-kit/components/xcss/). Primitives (Box, Stack, Inline, Flex, Grid, Text, Pressable) take token-only props, and `className` on ADS components is prohibited under the UI Styling Standard. — [atlassian.design/llms-full.txt](https://atlassian.design/llms-full.txt)
- **Atlassian ESLint rules (selected):** `ensure-design-token-usage`, `use-tokens-space`, `use-tokens-typography`, `use-tokens-shape`, `use-tokens-motion`, `no-deprecated-design-token-usage`, `use-primitives`, `use-primitives-text`, `ensure-proper-xcss-usage`, `no-unsafe-style-overrides`, `no-nested-styles`, `no-physical-properties`, `no-html-button`/`-anchor`/`-heading`/`-select`/`-textarea`/…, `no-deprecated-apis`, `no-deprecated-imports`, `no-banned-imports`. A separate UI Styling Standard plugin exists. — [Atlassian: ESLint plugin usage](https://atlassian.design/components/eslint-plugin-design-system/usage)
- **Shopify Polaris web components (stable 2025-10):** "Component styling is controlled by the merchant's branding settings and can't be overridden with custom CSS." Appearance is controlled only by `tone`, `color` and `variant`. Layout uses `s-stack`, `s-grid` and `s-box`, whose `gap`/`padding` take a "middle-out scale" from `small-500` to `large-500`. Named slots place custom content. — [Shopify: Using Polaris web components](https://shopify.dev/docs/api/polaris/using-polaris-web-components); [stable changelog](https://shopify.dev/changelog/posts/polaris-unified-web-components-are-now-stable)
- **Primer React v38 (27 Oct 2025):** removed `sx`, styled-system props and JS theming in favour of CSS Modules plus `className` and CSS variables. Packages are now ESM-only, and the stated rationale is smaller JS bundles and better client and server rendering. — [primer/react discussion #7086](https://github.com/primer/react/discussions/7086). An `@primer/styled-react` bridge keeps `sx` wrappers, deprecated by default — [styled-react README](https://github.com/primer/react/blob/main/packages/styled-react/README.md). Lint rule `no-system-props` — [eslint-plugin-primer-react](https://github.com/primer/eslint-plugin-primer-react/blob/main/docs/rules/no-system-props.md)
- **Panda CSS:** `strictTokens` allows only token values on token-backed properties, so raw `'red'`/`'123px'` are errors. `strictPropertyValues` throws on non-standard values for other properties. The escape hatch is an explicit `'[123px]'` syntax. — [Panda: Writing styles](https://panda-css.com/docs/concepts/writing-styles); [Panda config](https://panda-css.com/docs/references/config)
- **Measuring the boundary, Mews (11 Jun 2025):** a Babel plugin marks DOM nodes created by design-system components with `data-ds-element`. Adoption is design-system elements divided by all elements, sampled in production every 10 s via New Relic behind a flag. Products measured at 53% and 60%. They chose it because import counts and visual coverage distort. — [Mews engineering](https://developers.mews.com/design-system-adoption-metric-building/)
- **Static scans:** react-scanner counts component and prop usage and import sources. Teams note it measures change risk more than success — [zeroheight guide](https://zeroheight.com/help/guides/how-to-measure-the-dev-side-of-a-design-system/); [react-scanner usage note](https://blog.sapegin.me/til/react/finding-the-most-used-react-components-with-react-scanner/). Omlet (background) scans which props go unused, which values get passed, and which non-system components are heavily used — [Omlet](https://omlet.dev/blog/announcing-omlet/)
- **Sanctioned exceptions:** one practitioner's policy reads: use the system first; otherwise create a product-named local exception with a note; review exceptions monthly; promote repeated patterns; delete exceptions when the pressure goes. — [jpcasabianca.com: escape hatches](https://jpcasabianca.com/journal/design-system-escape-hatches/) (practitioner blog)
- **Figma side:** Slots (Schema 2025) let designers add layers inside instances without detaching them. — [Figma: Schema 2025 recap](https://www.figma.com/blog/schema-2025-design-systems-recap/)

### Inferences
- For a plain-CSS `--gv-*` system on React Aria, the equivalent of S2/ADS would be typed layout primitives whose spacing props take `--gv-space-*` names only. Components would expose no `style` and no `className`, or a single named `UNSAFE_className` that lint counts. Developers would also need lint that flags raw `<button>`/`<input>` when a system component exists.
- A "share of UI from the system" metric à la Mews is cheap to add to a demo back office built only from the system. It should read near 100%, and anything less exposes local styling.

### Gaps
- No public number was found for Atlassian's own adoption tracking (share of UI from ADS) in 2025–2026.
- No public override-count benchmark across companies was found.

## 4. The agent interface: making the system readable and enforceable for developers' agents

### Takeaway
By 2026, design-system context for agents ships as a hosted MCP server plus a machine-readable manifest. Storybook 10.3+ provides this for React. Chromatic publishes the MCP remotely, Atlassian runs a remote MCP, and shadcn ships registry MCP. Thin text files (llms.txt, DESIGN.md) supplement the MCP but don't replace it. Measured gains are real but modest to large depending on the system. The common failure is a manifest missing the guidance agents need, usually which component to choose and complete prop descriptions.

### Cited Findings
- **Storybook RFC (9 Sep 2025):** "agents will often *not* use the appropriate design system correctly, but generate its own component or styling solution". The proposed manifest carries names, descriptions, props (types/defaults/descriptions), example snippets from stories, docs pages and related components. Distribution could go via npm, a local build, a dev server or Chromatic. — [storybookjs/ds-mcp-experiment-reshaped #1](https://github.com/storybookjs/ds-mcp-experiment-reshaped/discussions/1)
- **Storybook MCP for React (23 Mar 2026, Storybook 10.3):** a benchmark on the Reshaped library, MCP docs versus baseline, gave "12.8% improved code usage", "2.76x faster" and "27% fewer tokens". The model and sample size were not disclosed. Agents run component and a11y tests and either fix or escalate. "Chromatic supports publishing Storybook MCP out of the box for free." — [Storybook blog](https://storybook.js.org/blog/storybook-mcp-for-react/)
- **Storybook MCP docs (10.6, "preview"):** three toolsets. **docs** (`docs-list`, `docs-show`, `docs-show-story`) needs `componentsManifest: true`. **dev** has `stories-changed`, `get-storybook-story-instructions`, `stories-preview`, `stories-find-by-component` and `review-create`. **test** has `test-run`, a "self-healing loop", and needs addon-vitest. The MCP runs on the dev server at `localhost:6006/mcp`, not from a static build. Composed Storybooks' manifests are merged. Suggested AGENTS.md text: "Never hallucinate component properties! … you MUST use the MCP tools to check if the property is actually documented." — [Storybook docs: MCP overview](https://storybook.js.org/docs/ai/mcp/overview); [MCP API](https://storybook.js.org/docs/ai/mcp/api)
- **Published MCP (Chromatic, vendor, 23 Mar 2026):** Chromatic builds an MCP server for every deployment, with branch and version permalinks. It inherits GitHub/GitLab/Bitbucket permissions. Product teams compose a design system's remote MCP with their own local one. React only. — [Chromatic blog](https://www.chromatic.com/blog/introducing-published-storybook-mcp-servers/); [Chromatic docs: MCP](https://www.chromatic.com/docs/mcp/)
- **Manifest failure mode (10 Jul 2026):** an agent nearly rebuilt existing components because default `react-docgen` returned empty props for intersection or index-signature types, and because "when to use Select vs Segmented vs Toggle" lived in the Docs tab (`parameters.docs.description.component`), which "the manifest never reads". The fix was `react-docgen-typescript` with a `propFilter`, plus moving selection guidance into the agent instructions file. "Documentation an agent can't retrieve might as well not exist." — [rachel.fyi](https://rachel.fyi/posts/storybook-mcp-reads-your-manifest-not-your-docs-tab)
- **Atlassian (28 May 2026):** a structured content model feeds the ADS MCP, skills, llms.txt and DESIGN.md. Reported "52% accuracy improvement in AI calls", "34% faster", "26% reduction in AI tooling calls" and "16% reduction in AI token usage". — [Atlassian: context engine](https://www.atlassian.com/blog/ai-at-work/atlassian-design-system-building-the-context-engine-for-the-ai-era). There is a remote MCP at `mcp.atlassian.com/v1/ads/public/mcp` and a local `npx @atlaskit/ads-mcp`, plus a topic-split llms.txt and an internal agent skill. — [atlassian.design/llms.txt](https://atlassian.design/llms.txt)
- **DESIGN.md versus MCP (Atlassian, 15 Jun 2026), login-screen task:** ADS MCP used 3.75M tokens, 5m01s and 35.1 turns. The ADS Skill used 4.43M, 5m23s and 36. DESIGN.md used 7.21M, 6m46s and 45.3, with about 2.7× the run-to-run variance. DESIGN.md "lacks code implementation guidance, causing agents to recreate components rather than import existing ones". Verdict: "a useful portability format … not a replacement for richer design system tooling." — [Atlassian: DESIGN.md](https://www.atlassian.com/blog/how-we-build/atlassians-design-md-is-here-what-we-learned-testing-portable-design-context-in-practice)
- **shadcn:** the MCP lets agents browse, search and install from public, private and `@namespace` registries configured in `components.json`, with auth headers from env. It works with Claude Code, Cursor, VS Code Copilot and Codex. — [shadcn: MCP](https://ui.shadcn.com/docs/mcp). Vercel's Registry Starter wires in "Open in v0", theming and MCP — [vercel/registry-starter](https://github.com/vercel/registry-starter)
- **v0 constraint:** "v0 is specifically trained on the default implementations of the `shadcn/ui` components and may struggle with any customizations." — [v0 docs: design systems](https://v0.app/docs/design-systems). Vercel (vendor, 22 Aug 2025) also concedes that "existing libraries or internal systems often lack the level of detail or structure models need" — [Vercel: AI-powered prototyping with design systems](https://vercel.com/blog/ai-powered-prototyping-with-design-systems)
- **Figma Make kits (vendor, 2 Apr 2026):** design-system authors package npm code components (public, or Figma's private registry) together with guidelines that "teach Make how to use them". Via the Figma MCP, "the same components and structure used in Make can be reused in code workflows". — [Figma blog: Make kits](https://www.figma.com/blog/introducing-make-kits-and-make-attachments/); [Figma help: design system package in Make kits](https://help.figma.com/hc/en-us/articles/35946832653975-Use-your-design-system-package-in-Make-kits)
- **Figma MCP (Schema 2025, 28 Oct 2025):** now GA, and teams can "add guidelines for how AI models should adhere to your design system". Code Connect UI maps Figma components to repo files with AI suggestions. — [Figma: Schema 2025 recap](https://www.figma.com/blog/schema-2025-design-systems-recap/)

### Inferences
- The developers' agents can only use govocal-ds context if it is reachable from their repo. A static Storybook on GitHub Pages serves no MCP, so the options are Chromatic-published MCP (React, free tier per Storybook), a shipped `components-manifest.json`/llms.txt inside the npm package, or a small hosted MCP.
- The agent interface itself should be tested like code. Publish a repeatable eval in the style of Storybook's Reshaped benchmark or Atlassian's DESIGN.md table, with fixed tasks, share of system components used, invented props/tokens counted, and tokens/time, and rerun it on each release.
- Selection guidance ("use X, not Y, when …") must live where the manifest or agent file reads it, not only in MDX.

### Gaps
- No independent (non-vendor) benchmark of Storybook MCP gains on a second library was found. The Reshaped numbers come from Storybook itself.
- No evidence was found on how well Figma Make kits keep output on-system in practice. The Make kits post has no named customers.

## 5. Code as the source of truth, Figma secondary: code-first systems, sync from Storybook, drift

### Takeaway
Tooling now runs in both directions. story.to.design generates Figma components from stories. Figma MCP "write to canvas" (beta) lets an agent build frames and components from existing library components. "Code to canvas" captures a running app only as flat layers. Code Connect maps Figma to code imports. Drift detection is mostly lint-style ("Check designs") on the Figma side and visual tests on the code side. The design team owns any sync; developers don't need Figma.

### Cited Findings
- **story.to.design (vendor):** a Figma plugin that "generates and maintains a full Figma library or UI kit directly from your Storybook" and refetches updated stories. — [story.to.design docs](https://story.to.design/docs/what-is-story-to-design); [Storybook→Figma guide](https://story.to.design/blog/from-storybook-to-figma)
- **Figma MCP write to canvas (beta, free during beta):** agents build "frames, components, variants, variables, and auto layout" via the `use_figma` tool, and "can build with the components, variables, and layout rules your team already uses". Limits: 20 KB per call, manual font uploads, and components must be published before Code Connect works. "Code to canvas" by contrast "captures a running app as flat layers, without a connection to your libraries." — [Figma developer docs: write to canvas](https://developers.figma.com/docs/figma-mcp-server/write-to-canvas). Write access since Feb 2026; Dev seats are read-only — [growthmethod (secondary)](https://growthmethod.com/figma-mcp-server/)
- **Check designs (early access, Oct 2025):** a Figma linter that surfaces layers that should use variables or styles before handoff. — [Figma: Schema 2025 recap](https://www.figma.com/blog/schema-2025-design-systems-recap/)
- **Code Connect as the anti-reinvention link:** Intercom's workflow depends on each Figma component carrying its code import path. — [rogerwong.me](https://rogerwong.me/2026/03/figma-mcp-compounding-design-system-domingo-widen)
- **Claude Design** imports the system from code (`/design-sync`) rather than from Figma. — [VentureBeat, 17 Jun 2026](https://venturebeat.com/technology/anthropic-ships-major-claude-design-overhaul-with-design-system-imports-code-round-trips-and-a-fix-for-its-token-burning-problem)
- **Practitioner drift view:** once design and code diverge, "drift has a way of accelerating" (vendor) — [Builder.io: Code is the source of truth](https://www.builder.io/blog/governance-beyond-figma)

### Inferences
- For a code-first team whose designers work in the coded components, Figma becomes an optional export. A code-first team can generate a Figma library from stories only if another role (marketing, other designers) still needs one. Flat "code to canvas" captures are not a library.
- Drift checks for a code-first system: the Figma library version label should equal the npm version, and Code Connect (if used) should map every component.

### Gaps
- No 2025–2026 primary case study was found of a company that formally declared code the source of truth and retired its Figma component library. The examples found are practitioner blogs.

## 6. What developers need contractually from a design-owned layer

### Takeaway
Developers need a published lifecycle per component, semver with migration guides and codemods for breaking changes, runtime and lint deprecation warnings, SSR-safe ESM output, i18n by design (strings as props, a locale provider), theming through CSS variables, measured performance, and a sanctioned path for what the system lacks. Primer, Atlassian, React Aria and Polaris each document parts of this. Developers keep the strategic calls (adopt or not, base library, integration).

### Cited Findings
- **Primer lifecycle (current):** Experimental, then Ready ("long-term support expected… Breaking changes trigger major version bumps and include migration guidance"), then Deprecated (documented alternative plus a consumer warning). — [Primer: Component lifecycle](https://primer.style/design/guides/component-lifecycle/). The older version **(background)** listed Alpha/Beta/Stable criteria: API feedback "sought from developers", design reviewed by Systems Designers, SSR compatibility, "no unnecessary performance regressions", and Stable meaning no breaking changes for at least a month. — [primer.github.io/contribute/component-lifecycle](https://primer.github.io/contribute/component-lifecycle/) (search excerpt). The two pages conflict on stage names; the newer one is simpler.
- **Breaking-change practice:** Primer v38 shipped a migration guide ("Migrating to CSS variables") and a deprecated compatibility package, and went ESM-only for SSR and bundle reasons. — [primer/react #7086](https://github.com/primer/react/discussions/7086); [styled-react README](https://github.com/primer/react/blob/main/packages/styled-react/README.md). Atlassian ships a Codemod CLI plus `no-deprecated-apis`/`no-deprecated-imports`/`no-deprecated-design-token-usage` lint. — [atlassian.design/llms.txt](https://atlassian.design/llms.txt); [ESLint usage](https://atlassian.design/components/eslint-plugin-design-system/usage)
- **i18n:** React Aria ships "localized strings for 30+ languages", handles "dates and numbers in many calendar and numbering systems, and supports right-to-left interactions". Locale is set via `I18nProvider`, and apps must set `lang`/`dir` on the root. — [React Aria: Quality, internationalization](https://react-aria.adobe.com/quality#internationalization)
- **Theming hooks:** Primer prefers "css variables over javascript theming" — [primer/react #7086](https://github.com/primer/react/discussions/7086). Polaris themes through merchant branding settings, with no CSS overrides — [Shopify docs](https://shopify.dev/docs/api/polaris/using-polaris-web-components)
- **Performance:** the S2 style macro emits atomic CSS at build time for bundle efficiency — [React Spectrum: Styling](https://react-spectrum.adobe.com/styling)
- **Escalation path:** lightweight RFCs for a missing component ask for the problem, existing alternatives, first consumers, a11y needs and maintenance cost. — [jpcasabianca.com](https://jpcasabianca.com/journal/design-system-escape-hatches/); Primer has a contribution page for adding new components — [Primer: Adding new components](https://primer-docs-preview.github.com/product/contribute/adding-new-components/)

### Inferences
- A design-owned layer earns developer trust by publishing the same artefacts as Primer and Atlassian: a status per component in Storybook, a changelog with semver, codemods or migration notes on majors, deprecation lint, an SSR/ESM build, and an i18n story (all copy via props, a locale provider, RTL stories).
- For a civic-participation product sold to cities in many languages, the i18n contract is not optional. Components should hold no literal user-facing strings and should format dates and numbers through the locale.

### Gaps
- No primary 2025–2026 exemplar of per-component bundle budgets in CI (for example size-limit thresholds) at a named large system was found in this pass. `developer_trust_and_ai.md` may cover it.

## 7. Reviewing component changes in Storybook: per-PR previews, Chromatic UI Review, visual diffs, agentic review (added scope)

### Takeaway
The working pattern for reviewing component changes is: every PR gets its own published Storybook, a visual diff against the merge base, and a UI Review in which designers and developers comment on specific snapshots and approve, as a required PR check. Chromatic provides all of this and also publishes the MCP per branch. Storybook's local agentic review (10.5+, experimental) curates the stories an agent changed, for the author's own loop. A plain Storybook on GitHub Pages is a release catalogue. It lacks per-PR previews, private access (Enterprise Cloud only), snapshot comments, visual diffs, approval checks and a reachable MCP.

### Cited Findings
- **Chromatic UI Review:** compares "the latest commit on the PR branch and the 'merge base' commit". Teams can "assign one or more reviewers", including designers and PMs. Discussions are "threaded and attached to the specific snapshot". A "UI Review" status check can be required. "All assigned default reviewers must approve for the Review to pass, which prevents a Review from being 'solo-approved'". Baselines must be approved before UI Review starts. Permissions sync from GitHub/GitLab/Bitbucket. — [Chromatic docs: Review](https://www.chromatic.com/docs/review/); [UI Review in dev-centric workflows](https://docs.chromatic.com/docs/dev-ui-review/); [feature page (vendor)](https://www.chromatic.com/features/review); a contributor-facing example of the flow in an open-source repo: [Bitwarden contributing docs: Chromatic UI Review](https://contributing.bitwarden.com/contributing/pull-requests/chromatic/)
- **Per-PR published Storybooks:** Chromatic links one per PR via a "Storybook Publish" status. One project removed its own gh-pages PR previews as redundant once that was reliable, though "chromatic.yml skips draft PRs". — [ZzAve/teambalance-app PR #406, 11 Oct 2026](https://github.com/ZzAve/teambalance-app/pull/406). Per-PR previews on GitHub Pages are DIY setups, see [lablup/ui-common PR #64](https://github.com/lablup/ui-common/pull/64) and [marimo PR #11223](https://github.com/marimo-team/marimo/pull/11223). WordPress Gutenberg tracked the need for branch-specific Storybook previews — [Gutenberg #71259](https://github.com/WordPress/gutenberg/issues/71259). Chromatic's GitHub Action automates publish plus visual tests — [Chromatic docs: GitHub Actions](https://www.chromatic.com/docs/github-actions/)
- **Access control:** "To publish a GitHub Pages site privately, your organization must use GitHub Enterprise Cloud." — [GitHub docs](https://docs.github.com/en/enterprise-cloud@latest/pages/getting-started-with-github-pages/changing-the-visibility-of-your-github-pages-site)
- **MCP per branch:** Chromatic serves an MCP per deployment, with branch permalinks and mirrored org permissions — [Chromatic blog](https://www.chromatic.com/blog/introducing-published-storybook-mcp-servers/). Storybook's own MCP runs only on the dev server — [Storybook docs](https://storybook.js.org/docs/ai/mcp/overview)
- **Agentic review (Storybook 10.5+, experimental):** the agent writes "a text summary of the work and curated collections of stories". It works in Storybook's review UI, not in published Storybooks, and shows a stale-review banner after later edits. — [Storybook docs: Agentic review](https://storybook.js.org/docs/ai/agentic-review). The MCP dev toolset's `review-create` pushes such a review — [Storybook MCP overview](https://storybook.js.org/docs/ai/mcp/overview). A Storybook PR removes the `experimentalReview` flag — [storybookjs/storybook #36562](https://github.com/storybookjs/storybook/pull/36562); tracking issue [#34823](https://github.com/storybookjs/storybook/issues/34823)
- **Figma links in stories (background):** addon-designs and Storybook Connect link stories and frames — [Storybook blog: design integrations](https://storybook.js.org/blog/design-integrations-for-storybook/); [Figma help: Storybook and Figma](https://help.figma.com/hc/en-us/articles/360045003494-Storybook-and-Figma)

### Inferences
- For designers and developers who collaborate on the library in Storybook, the GitHub Pages build should stay the released catalogue that developers read and import against. Review of unreleased component changes needs per-PR previews with snapshot comments, diffs against main, and a required designer approval next to the engineer code-owner approval. Chromatic provides that, or a self-hosted equivalent can (per-PR deploys, Storybook test-runner or Playwright screenshot diffs, GitHub PR comments).
- Agentic review suits the author's own loop (designer plus agent, locally, before opening the PR). Chromatic-style UI Review suits cross-role sign-off on the PR.

### Gaps
- No open-source tool with Chromatic-equivalent snapshot comments and approval checks was verified in this pass.

## 8. Concrete practices for a design-owned, agent-built component layer that developers compose from

### Takeaway
The practices below come from the findings above. Each one names what to do, who owns it, an exemplar, and how to check it. Ownership: **D** = design (the designers owning Storybook), **E** = developers/engineering, **D+E** = shared, with the named side deciding.

### Cited Findings
(Exemplar URLs are listed per practice. Each practice rests on the cited findings in sections 1–7.)

| # | Practice (what) | Owner | Exemplar | How to check |
|---|---|---|---|---|
| 1 | Style API surface is token-only: layout primitives (Stack/Inline/Grid/Box) whose `gap`/`padding` take spacing-scale names, and no free `style`/`className` on system components | D designs the scale; E approves the prop types | [Atlassian primitives/xcss](https://atlassian.design/llms-full.txt); [Polaris s-stack/s-box](https://shopify.dev/docs/api/polaris/using-polaris-web-components); [S2 `styles` prop](https://react-spectrum.adobe.com/styling) | A type test where `gap="13px"` fails `tsc`; component prop types have no `style`/`className` (or only an `UNSAFE_` one) |
| 2 | One named, countable escape hatch (`UNSAFE_className` or `'[raw]'` syntax), never silent overrides | D+E (E decides whether it exists) | [S2 UNSAFE_className](https://react-spectrum.adobe.com/beta/s2/release-notes.html); [Panda strictTokens escape](https://panda-css.com/docs/concepts/writing-styles) | Grep count of `UNSAFE_` in the demo app and consuming apps per release, trending down |
| 3 | Consumer lint pack: no raw values, no raw `<button>`/`<input>` where a component exists, no deprecated imports | D writes the rule list; E adopts it in apps | [Atlassian ESLint rules](https://atlassian.design/components/eslint-plugin-design-system/usage); [Primer `no-system-props`](https://github.com/primer/eslint-plugin-primer-react/blob/main/docs/rules/no-system-props.md) | The lint pack runs clean on the demo back office in CI; violations counted in the consuming repo |
| 4 | "Share of UI from the system" measured from rendered DOM (`data-gv` attribute on system nodes) | D owns the metric; E owns the instrumentation in apps | [Mews `data-ds-element`](https://developers.mews.com/design-system-adoption-metric-building/) | Script over demo/back-office routes reports ≥ 95% (demo should be ~100%) |
| 5 | Static usage scan of consuming code: unused props, local look-alike components | D | [react-scanner / zeroheight](https://zeroheight.com/help/guides/how-to-measure-the-dev-side-of-a-design-system/); [Omlet](https://omlet.dev/blog/announcing-omlet/) | Monthly report; local components that duplicate system ones become issues |
| 6 | Agent-grade component manifest: every component has a description, every prop has type plus description, and "use X not Y" selection guidance sits where agents read it | D | [Storybook manifest](https://storybook.js.org/docs/ai/mcp/overview); [manifest failure fix](https://rachel.fyi/posts/storybook-mcp-reads-your-manifest-not-your-docs-tab) | CI script over `components-manifest.json`: zero empty prop descriptions, zero components without a description |
| 7 | A hosted MCP or manifest that developers' agents can reach from their own repo (not only `localhost:6006`) | D publishes; E decides whether to wire it into product repos | [Chromatic published MCP](https://www.chromatic.com/blog/introducing-published-storybook-mcp-servers/); [ADS remote MCP](https://atlassian.design/llms.txt); [shadcn registry MCP](https://ui.shadcn.com/docs/mcp) | From a clean product repo, an agent calls `docs-list` against the URL and gets the component index |
| 8 | Agent rules file shipped with the package (AGENTS.md / llms.txt): "never invent props or tokens; check MCP first", the import path and the token prefix | D | [Storybook suggested AGENTS.md text](https://storybook.js.org/docs/ai/mcp/overview); [Atlassian llms.txt + skill](https://atlassian.design/llms.txt) | The file is in the npm tarball; an eval task (practice 9) shows zero invented props |
| 9 | Published agent eval per release: fixed screen-building tasks with and without context, measuring share of system components, invented props/tokens/icons, tokens and time | D runs it; E may define the tasks | [Storybook Reshaped benchmark](https://storybook.js.org/blog/storybook-mcp-for-react/); [Atlassian DESIGN.md vs MCP table](https://www.atlassian.com/blog/how-we-build/atlassians-design-md-is-here-what-we-learned-testing-portable-design-context-in-practice); [Atlassian 52% accuracy](https://www.atlassian.com/blog/ai-at-work/atlassian-design-system-building-the-context-engine-for-the-ai-era) | Results table in the repo, compared release to release |
| 10 | Self-healing loop inside the library: the agent must run component, interaction and a11y tests before a PR | D | [Storybook `test-run`](https://storybook.js.org/docs/ai/mcp/overview) | CI requires the test job; a11y violations = 0 on every story |
| 11 | Split review via CODEOWNERS: tokens/CSS/stories/docs → design reviewers; public API (exported names, prop types, package entry) → engineer reviewers; code-owner review required | D+E | [primer/react CODEOWNERS](https://github.com/primer/react/blob/main/CODEOWNERS); [Polaris CODEOWNERS](https://github.com/Shopify/polaris/blob/main/.github/CODEOWNERS) | CODEOWNERS file exists; branch protection shows "Require review from Code Owners" |
| 12 | Public-API diff on every PR (an API report or `.d.ts` diff) so engineers review only API changes, not every CSS tweak | E owns the gate; D triggers it | Inferred from the Primer lifecycle requirement that API feedback be sought from developers ([Primer lifecycle, background](https://primer.github.io/contribute/component-lifecycle/)) | A PR touching exported types fails CI without an engineer-owner approval |
| 13 | Per-PR Storybook with visual diffs plus a required designer UI Review check, with default reviewers so nothing is solo-approved | D | [Chromatic UI Review](https://www.chromatic.com/docs/review/) | Required status checks include visual tests plus UI Review; every merged UI PR has a review record |
| 14 | Small agent PRs with context-rich descriptions; big ones split; AI approvals labelled and queryable | D follows; E sets the limits | [Intercom AI approvals](https://www.intercom.com/blog/ai-is-approving-our-pull-requests-heres-how-we-made-it-safe); [Intercom Create PR skill](https://www.lennysnewsletter.com/p/how-intercom-2xd-their-engineering) | Median changed lines per PR; PR template fields filled; label query |
| 15 | Fix context, not review: the Atlassian failure list (bad imports, wrong token names, non-existent icons) caught by CI, not humans | D | [Atlassian failure modes](https://www.atlassian.com/blog/how-we-build/turning-handoffs-into-handshakes-integrating-design-systems-for-ai-prototyping-at-scale); [Faros](https://www.faros.ai/blog/ai-code-quality-senior-engineer-review-burden) | CI fails on any `var(--gv-…)` not defined in the token source, and on any unknown icon name |
| 16 | Lifecycle status per component (experimental / ready / deprecated), shown in Storybook, with runtime and lint warnings on deprecated ones | D labels; E agrees the "ready" bar | [Primer lifecycle](https://primer.style/design/guides/component-lifecycle/); [Atlassian `no-deprecated-apis`](https://atlassian.design/components/eslint-plugin-design-system/usage) | Every component has a status tag; deprecated ones log a warning and are linted |
| 17 | Semver, changelog and migration notes or codemods for every breaking change, plus a bridge package if a style API is removed | D writes; E reviews the majors | [Primer v38 + styled-react bridge](https://github.com/primer/react/discussions/7086); [Atlassian Codemod CLI](https://atlassian.design/llms.txt) | Changesets present; each major has a migration section |
| 18 | i18n contract: no literal user-facing strings in components (props or slots only); locale via provider; RTL and long-language stories | D+E | [React Aria I18nProvider, 30+ locales](https://react-aria.adobe.com/quality#internationalization) | Grep component source for English literals; an RTL (`ar`/`he`) story renders correctly |
| 19 | SSR- and bundle-safe output: ESM, static CSS (no runtime CSS-in-JS), size tracked | E sets the budget; D meets it | [Primer v38 ESM-only + CSS Modules](https://github.com/primer/react/discussions/7086); [S2 atomic CSS](https://react-spectrum.adobe.com/styling) | SSR render test of every component; size report per release (no exemplar threshold found) |
| 20 | Theming only through CSS variables (`--gv-*`), never through component props | D | [Primer: CSS variables over JS theming](https://github.com/primer/react/discussions/7086); [Polaris branding-only theming](https://shopify.dev/docs/api/polaris/using-polaris-web-components) | A theme swap story changes only variables; no component reads theme from JS |
| 21 | Sanctioned local exceptions: product-named, noted, reviewed monthly, promoted or deleted; plus an RFC path for missing components | D runs it; E files the requests | [Escape-hatch policy](https://jpcasabianca.com/journal/design-system-escape-hatches/); [Primer: adding new components](https://primer-docs-preview.github.com/product/contribute/adding-new-components/) | An exceptions list exists with dates; an issue template for requests exists |
| 22 | Figma secondary and design-owned: generated from stories when needed, version label equal to the npm version | D | [story.to.design](https://story.to.design/docs/what-is-story-to-design); [Figma write to canvas (library-aware)](https://developers.figma.com/docs/figma-mcp-server/write-to-canvas) | Figma library version equals the package version; developers' docs never link Figma |
| 23 | Access-controlled per-PR Storybook previews for unreleased component work | D+E | [GitHub Pages private = Enterprise Cloud only](https://docs.github.com/en/enterprise-cloud@latest/pages/getting-started-with-github-pages/changing-the-visibility-of-your-github-pages-site); [Chromatic permissions mirror the git host](https://www.chromatic.com/docs/review/) | A logged-out visitor cannot open a PR preview |

### Inferences
- Practices 1–5 answer the developers' "is it cemented in tokens?" doubt with things they can run. Practices 6–10 make the system enforceable for their agents. Practices 11–14 keep their approval where it matters without making them review CSS. Practices 16–20 are the contract that lets them keep the strategic calls on adoption, base library and integration.
- Several of these practices are cheap for a ~55-component plain-CSS system: CODEOWNERS, a manifest CI check, a token-existence check, and the DOM-share metric on the demo back office. The costly ones are hosted per-PR review with comments (Chromatic or similar) and a published agent eval.

### Gaps
- Practice 12 (an API-diff gate) and the bundle budget in practice 19 rest on inference plus older Primer criteria. No 2025–2026 public exemplar was found of a design-owned repo that gates only API changes on engineer review.
- No source measured whether designers acting as owners of production component code (rather than contributors) produce systems with fewer or more defects. That evidence does not appear to be public yet.
